# Bug 速通阶段（Intake / Fast Fix / Smoke）

速通模式的通用语义（唯一询问点、不可省清单、欠账台账 schema、恢复）见 [fast-track-contract](../../dd-workflow-runtime/references/fast-track-contract.md)；本文件只写 Bug 领域的做法。

## 1. Intake

### 1.1 复述模板（一次询问，三段话）

用通俗语言复述，让用户能一句话确认或纠正：

1. **症状**：什么操作、在什么环境、看到什么（带上报错、日志片段或截图来源）；
2. **期望**：正确情况下应该看到什么；
3. **修复范围**：这次修到哪里为止——只治当前症状、还是连带修同类调用点；明确不做什么。

复述后**不再就排查细节提问**。未确认（null、取消、空输入）→ 按 [ask](../../dd-workflow-runtime/references/ask.md) 重问。

### 1.2 工作环境（强制新建隔离 fix worktree，不询问）

**首次建立执行环境时必须新建隔离 fix worktree，且在修改任何项目产物（代码、测试、规格、项目文档等交付范围内文件）之前完成**，遵循 `dd-git-workflow` 的 branch 与 worktree 规则。这不是推荐项，也不询问用户。

只有两种例外：

- 恢复任务或父工作流已提供 fix worktree → 复用并验证，不重新创建；
- 用户明确要求在当前工作区修改 → 允许，但必须把原因写入状态 `reason`。

除此之外不允许默认就在当前工作区改代码。runtime 状态文件与工作流内部证据文件按 runtime 合同处理，不属于项目产物修改。

工作环境确定后立即持久化状态，写入 `fast_track=true`、`track_phase=fast-track`、`requirement_confirmed=true`，并记录症状、期望与日志来源。

**tracking 绑定（Intake Gate 前，速通工作流的绑定 Gate 就是 Intake）**：按 [task-tracking](../../dd-workflow-runtime/references/task-tracking.md) §3 执行一次绑定尝试，并把结果按该合同落盘。绑定语义、失败矩阵与重试策略完全由该合同定义；绑定失败**不阻塞本 Stage**，也不因此向用户发问（速通阶段唯一询问点仍是症状复述）。

Intake Gate：症状复述已获用户确认、工作环境已持久化、tracking 绑定结果已按 owner 合同落盘。

### 1.3 只授权诊断时

用户只要诊断、没说修：不进入 Fast Fix，输出定位结论与证据后停止，交接 `dd-bug-fix-workflow`。不得把诊断请求扩成修复授权。

## 2. Fast Fix

### 2.1 执行方式

- 快速定位：沿数据流、调用栈、近期改动和日志找最可能的那一处，不追求穷举排查；
- 最小修复：只改与症状直接相关的一处，不顺手重构、不顺手改命名、不夹带无关文件；
- 需要选择时（改调用方还是改被调用方、加防御还是修数据源）直接选推荐项，把「选择 + 一句话理由」追加到 `decisions`；
- 确实需要一次改多处时，允许合并修改，但必须在状态里记为"多变量修改，因果待补对照验证"，并在台账里登记 `root-cause` 欠账；
- 仍然遵守项目规则（lint、格式化、命名），"速通"不等于"随意"。

### 2.2 询问例外（只有这四种可以停）

按 fast-track-contract §3.2：不可逆或外部可见动作、缺授权且无推荐替代、症状描述自相矛盾或关键输入缺失、已确认期望本身不成立。除此之外一律继续。

授权边界单独处理：commit／push／merge／发布仍需动作级授权，缺失时记 `not-authorized` 并停在该动作边界，不阻塞速通产出。

### 2.3 需要停下来交接正式流程的信号

- 症状无法稳定复现，且定位只能靠猜；
- 修复会改变既有行为或既有回归预期（超出复述确认的范围）；
- 触及持久化格式、并发模型、兼容性、安全或权限；
- 需要跨模块或跨服务改动。

交接时带上症状、期望、当前修改、已有日志与 `decisions`，按 [diagnosis-and-verification](../dd-bug-fix-workflow/references/diagnosis-and-verification.md) 的正式规则继续。

## 3. Smoke

### 3.1 冒烟自证（必须真实跑通）

- 真实运行复述时描述的操作路径，确认症状消失；
- 用户可见 Bug 按 [ui-evidence](../../dd-workflow-runtime/references/ui-evidence.md) 取真实路径证据，不接受内部状态、mock 或日志代替；
- 跑与改动直接相关的既有测试，确认没有把别处跑坏；这一步只是**不跑坏**的初步证据，不是回归 CI。

### 3.2 交付可用产物

把「怎么立刻验证」交给用户：启动或复现步骤、该看哪个位置、期望结果。用户此刻应该能亲手确认症状消失。

### 3.3 默认欠账清单（逐条登记，不得漏项）

| kind | 速通阶段为什么不做 | 关闭所需证据 |
|---|---|---|
| `root-cause` | 只做了最可能定位，没证明因果 | 日志／数据流／最小实验之一的根因证据；多变量修改时还需单变量对照实验结论 |
| `regression` | 没写复现测试 | 复现测试在回退实现上红、在修复实现上绿的实际运行记录 |
| `determinism` | 没做确定性验证 | 同一份修复重复执行结论一致的验证记录 |
| `ci` | 没跑回归 CI | 最终 SHA 上的完整回归 CI 运行记录 |
| `docs` | 没同步长期文档 | 受影响的长期文档已同步，或明确"无需更新"的结论 |
| `ui-evidence` | 只在用户可见 Bug 时登记 | 真实路径证据与新鲜度绑定（非用户可见 Bug 时不登记） |

台账写入状态后立即进入 Backfill，不等用户再次要求。

### 3.4 本阶段禁止的宣称

不得说"根因已查明""已修复并验证""可以交付"。交付的是**症状已消失的可用产物**，不是已证明根因的修复。
