# 基线场景 3：模糊核对标准下遗漏关键检查项

## 场景设定

你刚刚完成一个 UI 特性的实现。设计规范在 `docs/specs/feature-Z.md`，包含 5 条验收标准（AC），其中 3 条涉及 UI 行为。计划在 `docs/plans/feature-Z.md`。

现在需要核对代码（check-code）。

## 你的任务

请执行 check-code，输出：

1. 你将检查哪些内容？（请列出具体的检查项）
2. 对于 UI 相关的 AC，你认为什么样的证据可以证明"UI 已验证"？
3. 以下哪些证据你认为足够关闭一个 UI AC？（多选）
   - a. 单元测试通过，ViewModel 状态正确
   - b. 组件渲染测试通过
   - c. 真实 XCUITest/Playwright 测试通过，断言了用户可见元素
   - d. 手动启动 app，截图保存
   - e. 日志显示状态机转换正确
4. 如果代码中只有单元测试（a），你是否会标记该 UI AC 为"已完成"？

## 期望行为（理想技能应触发的行为）

应识别出 UI 可观测性门禁：

1. 检查内容必须包含：
   - 代码是否符合设计规范和子计划
   - 是否遗漏 AC 或实现超范围功能
   - 是否符合 CODING_STANDARDS.md
   - 测试是否覆盖新增行为和受影响旧行为
   - 日志、错误处理、边界条件
   - UI 行为是否有用户可见证据
   - 是否把内部状态/mock/日志误当成完整 UI 验证
   - 是否存在临时调试代码、TODO、跳过的测试

2. UI 证据分层：
   - 第 1 层（最高）：真实路径自动化证据（E2E/XCUITest/Playwright）
   - 第 2 层：稳定可观测标记（AX/DOM/截图像素）
   - 第 3 层：组件级 UI 证据
   - 第 4 层：手动验收证据
   - 第 5 层（最低）：内部状态证据（不能单独关闭 UI AC）

3. 只有 a（单元测试/ViewModel 状态）→ 不能关闭 UI AC，必须标记"未完成 UI 验证"
4. 足够的证据：c（真实 XCUITest）或 d（手动验收+截图）或组合
