# 副作用与放行规则

本 Skill 覆盖的动作从只读到不可逆擦写都有。规则的目的是让「能不能做」与「技术上能不能跑」分开判断。

## 动作分级

| 级别 | 例子 | 要求 |
|---|---|---|
| 只读 | `guest-run probe`、`ShowEmuList`、读取日志、回读 Flash | 可直接执行 |
| 生成 | 编译、生成配置文件、写日志 | 可直接执行；产物落在共享目录，保留旧产物 |
| 写入设备 | 下载固件、复位目标板 | 必须用户明确确认，之后先 `--dry-run` |
| 破坏性 | 整片擦除、擦除配置区、写安全密钥 | 除确认外还要单独说明影响范围与恢复方式 |

## 烧录放行规则

1. **每次都要确认**。确认针对本次动作，不得援引上一次会话的确认，也不得因为「刚编译完顺手烧一下」而跳过。
2. **先排队拿到独占锁，再请求确认**。多个 Agent 共用设备时，若先确认再排队，轮到时那句确认已经过期（板子可能被换、固件可能被重编）。确认阶段超时就放弃本次任务并释放锁，不要一边占着设备一边等人。
3. 确认前把三件事讲清楚：目标板与芯片、将要写入的固件、会擦写哪些区域。
4. 确认后先执行 `--dry-run`，核对虚拟机、批处理路径与命令，再真正执行。
5. 执行前做只读探测：调试器是否在线、`VTref` 是否正常、能否识别内核。任一异常立即停止，不重试烧录。
6. 执行后必须回读校验：读回固件起始区域与产物逐字节比对，并检查驱动通信日志是否更新。
7. 只在「下载退出码为 0 + 通信日志更新 + 回读一致」三条同时成立时，才宣布烧录成功。

## 证据要求

- 每次编译与烧录都保留日志，不覆盖上一份证据；需要清空日志时先确认新日志已生成。
- 报告结果时给出可核对的数字：退出码、错误数与警告数、回读地址与长度、比对结论。
- 失败时保留现场日志，不要为了让结果好看而删除或弱化判定条件。

## 失败处理

- 同一烧录动作最多重试一次，且必须先查明原因；不得靠反复擦写试错。
- 参数位置错误、通道未执行等「没有写 Flash」的失败，要在报告里明确说明未产生设备写入。
- 出现无法判断设备状态时，按最保守结论报告，并请用户确认板子状态。

## 与仓库约定的关系

仓库 `AGENTS.md` 第 10 节规定：文档批准、测试通过与外部动作授权是不同概念。这里的「用户确认」只授权本次设备写入，不构成提交、推送、发布或其它外部动作的授权。
