# 架构决策与后续计划

本文记录 2026-11-09 关于「与 Parallels 通讯是否要写成 Skill 或做成 MCP」的讨论结论，以及今后需要做的事情。它是规划记录，不是执行规则；执行规则以 `SKILL.md` 和 `references/` 为准。

## 一、讨论记录

### 问题背景

`DCM_CMT2300A` 工程放在 Mac 上，经 Parallels 共享给 Windows 虚拟机，由 IAR EWARM 编译、J-Link 烧录。本次打通了命令行编译与烧录，但后续还要支持其它嵌入式芯片的编译与其它烧录器，因此需要决定是否把这套能力固化为 Skill 或 MCP。

### 结论：三层分工，不是二选一

| 层 | 职责 | 形态 |
|---|---|---|
| 能力内核 | 传输、编译、烧录、校验本身 | 与 AI 无关的命令行工具 `bin/guest-run` 与配方 |
| 知识层 | 决策树、踩坑清单、调用约定、安全红线 | 本 Skill（现在就做） |
| 协议层 | 给其它客户端的结构化工具与资源 | MCP server（满足条件后再做） |

核心判断：**真正该抽出来的是一个与 AI 无关的命令行内核**。现在 `cli_build_mac.sh` / `flash_mac.sh` 把「怎么进虚拟机」和「怎么编译烧录」揉在一起，这才是扩展会痛的地方。三层各司其职，互相不替代。

### 为什么现在做 Skill、不做 MCP

Skill 最适合承载这类领域知识：`cmd.exe` 不接受 UNC 当前目录、`cspybat --download_only` 必须放在 `--backend` 之前、`prlctl` 服务故障要回退、烧录前要查 `VTref`、烧完要回读比对。这些是「什么时候用哪个、哪里会踩坑」的判断，工具 schema 装不下。项目级软链接随仓库共享，新增一个配方只是加一个脚本和一段说明。

MCP 目前是过度工程：只有这台 Mac 上的会话在用，能力本质是「执行一条命令并读回日志」，换成常驻进程与 JSON-RPC 收益有限，还要注册、授权、保活、调试。

### 扩展的正确姿势

新增芯片或烧录器不应变成不断增加工具函数或脚本分支，而应是一张注册表：芯片映射到构建配方与调试配置，烧录器映射到烧录配方与回读方式，并记录 `VID/PID` 以及**该设备必须直通到哪台虚拟机**。换烧录器真正的麻烦是 USB 直通，与命令通道是两件事，必须显式记录。

### 现有通道的债务

存根方案可用但属于绕行：硬编码共享路径与存根名、`/tmp` 固定目录要先结束旧实例、日志轮询、每个流程手写批处理。应做成可替换的传输层：首选 `prlctl exec`（同步、直接取标准输出），服务不可用时回退到共享应用存根（异步、日志回传）。这样以后换 VMware、换原生 Windows 主机或远程构建机，都只是换一个适配器。

### 什么时候才上 MCP

满足任一条再做：需要给 Claude Code、Cursor、持续集成或其它 Agent 直接调用；需要把烧录做成带确认与审计的工具级守卫；需要查询「当前在线的虚拟机与烧录器」这类资源；需要并发任务与状态。

### 落地顺序

1. 抽出 `guest-run` 传输层，双通道回退；
2. 把现有编译与烧录流程收进统一内核；
3. 写项目级 Skill，固化决策树与踩坑清单；
4. 需要跨客户端时，MCP 只包一层同一个命令行内核，不重写逻辑。

用户已确认先做第 1 步与第 3 步，并把讨论内容与待办单独记录成本文。

## 二、已完成

- `bin/guest-run`：`run` / `exec` / `probe` 三个子命令，自动发现虚拟机，优先 `prlctl exec`、失败回退共享应用存根，统一返回 JSON，支持 `--dry-run`、`--human`、`--transport`、`--share-root`、`--mac-home`。
- 并发控制（2026-11-25）：`bin/guest-run` 内置 `flock` 独占锁与票号排队，默认按设备串行；新增 `status` 子命令、`--lock-scope` / `--lock-key` / `--lock-timeout` / `--job-id` / `--log-mode` 参数、退出码 `2`（等锁超时）；临时批处理改为按任务命名，日志清空前留档 `.prev`。
- 工程侧 `iar/cli_build_mac.sh` 与 `iar/flash_mac.sh` 改为调用统一内核，不再各自维护存根复制与日志轮询。
- `SKILL.md` 与四份 `references/`：通道契约、配方决策树、踩坑清单、副作用放行规则。
- `tests/test_guest_run.py`：路径换算、退出码解析、干运行、探测，以及锁互斥、等锁超时、崩溃自恢复、队列可见性、日志留档等并发用例（29 项）。

## 三、今后需要做的

按优先级排列，前两项是后续扩展的前置条件。

1. **修复并实测 `prlctl` 通道**。当前 dispatcher 服务报「登录失败」，回退通道承担了全部流量，`prlctl exec` 分支尚未在真实环境验证。在 Mac 终端执行 `sudo launchctl start com.parallels.desktop.launchdaemon`（或重启 Parallels Desktop）后，用 `bin/guest-run run --transport prlctl` 验证，并确认 UNC 路径的批处理能否被 `cmd.exe /C` 直接执行；必要时在同步通道里也加 `pushd` 包装。
2. **落地配方与注册表（原方案第 2 步）**。抽出 `recipes/` 与 `registry.yaml`：芯片到构建配方、烧录器到烧录配方与回读方式，含 `VID/PID` 与 USB 直通目标虚拟机的记录。把现有 IAR 与 J-Link 流程改成查表驱动，而不是脚本内硬编码。
3. **新增编译配方**：Keil MDK 的 `UV4.exe -b`、ChessDE 的命令行入口、GCC Makefile。每新增一个都要写明工程文件路径是否需要盘符化、预构建脚本如何注入。
4. **新增烧录配方**：ST-Link 的 `STM32_Programmer_CLI`、CMSIS-DAP 的 pyOCD、串口 bootloader（项目里 `python/ylSerial.py` 是现成线索）、JFlash。每个都要写明连接确认、擦写范围、回读地址与校验方式。
5. **USB 直通清单化**。虚拟机层面记录每种烧录器接到哪台虚拟机，并在烧录前做只读探测；缺少直通时明确报错，不要静默换设备。
6. **通道增强（并发部分已完成）**：`exec` 已支持按任务命名的临时批处理与独占锁；剩余的是结构化标准输出、传输层接口化（可替换成 VMware、原生 Windows 或 SSH），以及共享根与虚拟机名改为注册表提供、去掉默认值依赖。
7. **MCP 适配层**（触发条件见上）。工具只包一层命令行内核，把烧录做成带确认与审计的独立工具，不复制 Skill 里的知识。
8. **验证补全**：按仓库 `writing-skills` 的要求补 Skill TDD 压力场景（尤其是「时间紧、跳过烧录确认」「上次确认过所以这次不用问」两类），并把合同测试接入持续集成。
9. **持续集成**：让构建脚本在无 AI 会话时也能跑，命令行内核不依赖对话上下文。

## 四、明确不做

- 不把能力逻辑写进 MCP server 再让 Skill 反过来调用 MCP；
- 不用图形界面自动化点击 Windows 窗口，本机自动化权限已被拒绝；
- 不通过修改用户工程配置来规避 UNC 限制（命令行侧用盘符路径即可）；
- 不把 `~/.workbuddy-ai/skills` 整个目录替换成软链接，现有技能由仓库的 `bin/link-agent-skills.sh` 逐个同步；
- 不擅自提交或推送本仓库改动，外部动作需要单独授权。
