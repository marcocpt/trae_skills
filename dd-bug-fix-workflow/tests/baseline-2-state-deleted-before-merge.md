# 基线测试 2：步骤 7.1 删除状态文件后压缩导致完全失忆

## 场景

bug 修复工作流已进入步骤 7.1（合并到 develop），状态文件被删除但 `git merge --no-ff` 尚未执行。此时会话上下文被压缩。

压缩后用户消息："继续在 fix/F3.1-toolbar-align-hintmode worktree 上工作，更新状态文件，对照 HintMode 修复"（描述的是上一个已修复 bug 的内容，但用户以为还没修）。

## 预期行为（修改后技能）

智能体应按以下顺序恢复：

1. 发现状态文件已被删除
2. 通过 `git log` 检查 fix 分支与 BASE_BRANCH 的提交差异，发现已存在 bug 修复 commit
3. 识别"bug 已修复，待合并"状态
4. 询问用户：是直接合并到 BASE_BRANCH，还是开新一轮 bug 修复
5. 用户确认后执行合并（步骤 7.1）或开新一轮（步骤 0）

## 当前基线行为（修改前预期失败）

1. ❌ 智能体发现状态文件不存在
2. ❌ 默认按步骤 0 重启新一轮 bug 修复流程
3. ❌ 用户描述的 bug 内容（对照 HintMode 修复）被误当作新 bug
4. ❌ 重新扫描日志、重新 TDD、重新修复——但实际 commit 已存在
5. ❌ 与 BASE_BRANCH 比对时才发现代码已就绪，浪费整轮 TDD 时间
6. ❌ 用户被迫打断："bug 修复其实已经完成"

## 压力因素

- 状态文件删除时机过早：步骤 7.1 的"先删除状态文件"在合并执行之前
- 会话压缩后无任何持久化信号标识"已进入步骤 7.1"
- 用户描述的 bug 内容与已修复 bug 相同（用户记忆也未刷新）
- 智能体缺乏"状态文件不存在 ≠ 全新开始"的判别机制

## 根因

`dd-bug-fix-workflow/SKILL.md` 步骤 7.1：

> **先删除状态文件**（在离开工作树前，遵循 dd-shared-state 删除模板）
> ```bash
> cd "$main_root"
> git checkout "$BASE_BRANCH"
> git merge --no-ff <工作树分支>
> ```

删除状态文件与执行 `git merge` 之间存在窗口期，会话压缩在此窗口内发生时，智能体无法恢复"待合并"状态。正确做法应该是：

- 状态文件先更新 `current_step=7.1` 标识"合并中"
- 执行 `git merge` 成功后再删除状态文件
- 或：合并前先在状态文件中标记 `merge_in_progress=true`，合并后清除

## 备注

此场景在 2026-07-16 真实发生过：用户上轮 bug 修复（commit `9b31576c` + `9447fc09`）已 push，进入步骤 7.1 删除状态文件后会话压缩，智能体错误地从步骤 0 重启，浪费了完整一轮 TDD 调查。
