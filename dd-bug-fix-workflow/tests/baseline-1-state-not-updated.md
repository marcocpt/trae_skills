# 基线测试 1：中间步骤状态文件未更新导致恢复失败

## 场景

bug 修复工作流进行到步骤 4（确认是否继续），用户已完成：

- 步骤 0：需求确认（已选当前 worktree）
- 步骤 1：创建/验证工作树（状态文件已写入，current_step=1）
- 步骤 2：TDD 调试修复（XCTest 绿灯）
- 步骤 3：代码同步（commit + push 成功，AI-test 已同步）
- 步骤 4：进入「确认是否继续」询问

此时会话上下文被压缩。压缩后用户消息："继续"。

## 预期行为（修改后技能）

智能体应按以下顺序恢复：

1. 读取状态文件 `bug-fix-state.json`
2. 发现 `current_step=4`（步骤 3 完成时已更新）
3. 直接进入步骤 4 出口判定，询问用户是否进入步骤 5
4. 用户选「继续」 → 更新 `current_step=5`，进入步骤 5

## 当前基线行为（修改前预期失败）

1. ❌ 智能体读取状态文件，发现 `current_step=1`（从未更新）
2. ❌ 误以为还在步骤 1（创建工作树阶段），重新执行步骤 1 验证
3. ❌ 或因状态文件指向已存在 worktree，跳过验证后进入步骤 2
4. ❌ 重新执行步骤 2 的 TDD 流程，可能覆盖已有 commit 或重复写测试
5. ❌ 用户被迫手动纠正："bug 已经修完了，跳到合并步骤"

## 压力因素

- 状态文件存在但 `current_step` 字段已过时
- 会话压缩丢失"刚才已经完成步骤 3"的对话记忆
- worktree 路径和分支名仍正确，欺骗性地暗示"状态正常"
- 用户简短回复"继续"未指明具体步骤，依赖智能体从状态文件恢复

## 根因

`dd-bug-fix-workflow/SKILL.md` 顶部「上下文恢复机制」声明：

> **更新 `current_step`**：每完成一个步骤

但步骤 2 / 3 / 4 / 5 / 6 的出口判定章节均无「更新状态文件 `current_step=N`」的强制要求。智能体仅在步骤 1 写入一次 `current_step=1`，之后不再更新。会话压缩后状态文件无法反映真实进度。
