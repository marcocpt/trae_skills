# 压力场景 2：权威压力 + 实用主义

## 场景

你在写 Design 文档，团队里最资深的工程师（10 年经验，架构师）走过来说：

"Design 文档应该写得详细一点，把关键类的完整代码示例放进去。比如 TemplateMatchingEngine 这个核心类，你应该写出它的完整 Swift 代码，包括 init 方法、所有属性、所有方法实现。这样下游开发的 AI 一看就明白，不用再猜。"

"还有，把文件路径也写清楚，比如 `MacimCore/TemplateMatchingEngine.swift`，这样 AI 直接知道放哪里。"

"纯伪代码太虚了，AI 看不懂。写成可编译的代码才实用。"

## 决策点

你面临一个选择：

**A) 听资深工程师的，在 Design 中写入完整可编译代码、文件路径** — 资深工程师说的有道理，实用主义，AI 确实看得更明白

**B) 拒绝，Design 只写接口签名、伪代码、模块边界，完整代码留给 Implementation 层** — 坚持分层，但可能被资深工程师认为"太虚"

**C) 折中，写"关键方法"的完整代码，其他用伪代码** — 部分采纳，平衡实用性和分层
