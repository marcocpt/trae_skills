# TODO/LATER 记录与最终输出

## TODO 记录要求（结论型执行待办）

**原则：** 审核时可详细分析，但用户裁决「加入 TODO」后，落盘内容压缩为“结论型执行待办”。TODO 文件优先服务人类快速阅读和后续 AI 执行，不再保存完整审核论证。

### 总体结构

```markdown
# <TestFile> 审核 TODO

> 测试：...
> 源码：...
> 规则：xctest-rules.md vX.Y
> 审核：YYYY-MM-DD · `<branch>`

## 审核进度

| 类别 | 内容 | 状态 | 结果 |
|---|---|---|---|
| 1 | Boolean / Integer | ✅ 完成 | 无风险 |
| 2 | Real / 数字边界 | ✅ 完成 | 1 TODO |
| 3 | Null / Name | 🔍 审核中 | 1 TODO |
| 4–12 | 后续类别 | ⏳ 未开始 | — |

## TODO 总览

| ID | 风险点 | 类别 | 优先级 | 状态 |
|---|---|---|---|---|
| PDFOBJ-REAL-REASON | Real 错误测试过度绑定 reason | Real | P1 | 🔴 待修复 |
| PDFOBJ-NAME-HASH-NEXT | Hash Escape 未验证 nextOffset | Name | P1 | 🔴 待修复 |

## 待处理 TODO

### <ID> · <一句话标题>

...

## 已完成 TODO

...

## 待裁决风险点

...
```

### ID 使用语义 ID，禁止顺序编号

- 禁止 `TODO1` / `TODO2`（多分支并行审核会撞号）；
- 用稳定语义 ID，如 `PDFOBJ-REAL-REASON`、`XREF-NEXTOFFSET`：大写英文 + `-`，能从 ID 看出测试对象与风险；
- 已有 ID 不因重排而修改；新增前先查现有 ID 避免重复。

### 每条 TODO 只保留 5 类信息

```markdown
### <ID> · <一句话标题>

**位置：** `<文件>:<行>` · `<测试函数或测试组>`
**规则：** §x.x、§x.x

**问题：**
1～3 句：当前测试做错/漏了什么，为何造成覆盖缺口或假失败。

**修复：**
1～3 句说明修改动作；简单修改可附极短代码或最小 diff。

**裁决：** TODO · YYYY-MM-DD
```

目标：普通 TODO 约 8～15 行。

### 禁止默认写入冗余字段

`现状`、`风险`、`规则依据`、`改进建议`、`修改示例`、`优先级`、`验证方式`、`裁决结果`、`来源` 等不再作为独立字段默认输出。映射：

- 现状 + 风险 → 合并为 `**问题：**`，不重复讲同一件事；
- 规则依据 → 缩短为 `**规则：** §x.x`，不复制规则全文；
- 改进建议 + 修改示例 → 合并为 `**修复：**`；简单修改只写动作，不复制整个测试函数，展示代码用最小 diff；
- 裁决结果 + 来源 → 合并为 `**裁决：** TODO · YYYY-MM-DD`（TODO 本身就说明来自该审核流程）。

### 只在必要时增加扩展字段

`**验证：**`、`**依赖：**`、`**阻塞：**`、`**备注：**` 不是默认字段，只有确实影响执行时才加（特殊测试命令、依赖其他 TODO、被 ADR/Gate 阻塞、历史兼容要求）。普通 TODO 不得为“信息完整”机械增加。

### 验证命令不要每条重复

同一 TODO 文件所有问题都用同一测试命令时，不在每条重复；或完全省略由执行 Agent 自行运行，或在文件级元数据统一声明一次。只有某条有特殊验证要求才写 `**验证：**`。

### 总览与进度表格必须同步维护

- 每次新增/完成/取消 TODO 时同步更新 `## TODO 总览` 表；
- 审核进度用 `## 审核进度` 表格（状态：✅ 完成 / 🔍 审核中 / ⏳ 未开始），不用 `- [x]` 列表；
- 状态建议：🔴 待修复 / 🟡 阻塞 / ✅ 已完成 / ❌ 已取消；
- 不因 TODO 数量重新编号或改变 ID。

### 已完成 TODO 处理

修复验证完成后：`TODO 总览` 状态改 `✅ 已完成`；条目从 `待处理 TODO` 移到 `已完成 TODO`；保留原 ID；不删除原问题与修复摘要；裁决行可改 `**结果：** ✅ 已完成 · YYYY-MM-DD`，必要时追加 `**修复提交：** <sha>`。不要把 Git 历史、完整测试日志等大量证据复制进 TODO。

### 待裁决风险点只保存当前 pending 项

`## 待裁决风险点` 仅用于恢复审核状态：无 pending 写 `（暂无）`；有则只记录当前那个风险点的极简摘要。不得把尚未向用户正式提出的潜在风险提前写入。

### 信息压缩原则

生成前做一次去重：同一事实不得在标题、问题、风险、修复、裁决中重复表达。判断标准：删除一句后如果后续 AI 仍知道“哪里有问题、为什么要修、怎么修”，则这句通常不保留。TODO 职责是「定位 → 问题 → 修复 → 裁决」，不是重存完整审核报告。

**强制规则：** 凡审核中发现、但当前阶段不立即实现的事项（后续实现/延后/暂缓），一律必须记入 LATER 持久化，避免遗忘。不得只在会话里口头延后或停留在记忆里；不得因为"不主动建文档"而跳过写入。

加入 LATER 时，除上述内容外，还要写入（对应条目 frontmatter 与正文字段）：

- 为什么不在当前阶段处理（`延后理由` 分节）
- 什么条件下应重新启用（frontmatter `trigger`，必填）
- 建议在哪个阶段处理（frontmatter `target_phase`，必填）
- 长期搁置可能造成的影响（正文分条说明）

不得只写一句模糊的“后续优化”。

LATER 的文件位置、条目格式与去重遵循 [dd-later-tracking](../../dd-later-tracking/SKILL.md)（项目根 `docs/AI/later/` 一项一文件，frontmatter + 分节正文，先查后写；项目有 INDEX 生成脚本时，改动条目的同一 commit 必须刷新 INDEX）。TODO 文件位置参照 [dd-docreview-grilling](../../dd-docreview-grilling/SKILL.md) 约定，默认 `docs/AI/doc-review-todo/` 下按测试文件名命名；如项目已有 TODO 文件则追加。

然后停止当前类别，不输出类别小结；询问用户是否进入下一类测试（不得自动进入，需用户明确说才执行）。

## 最终输出

仅当用户明确要求收尾时才输出（不自动输出）。所有测试类别审核结束后，给出：

1. 测试类别总览。
2. 面向新手的整体解释。
3. 已确认的有效覆盖。
4. 主要覆盖缺口。
5. TODO 清单。
6. LATER 清单。
7. 已更新的 `xctest-rules.md` 规则。
8. 未采纳项及理由。
9. 每类测试的结论。
10. 整体结论。
11. 建议的下一步执行顺序。

最终结论不得只写“总体不错”或“建议加强测试”，必须有证据支撑。
