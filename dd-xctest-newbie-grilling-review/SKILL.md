# XCTest 新手向交互式审核

## 目标

用户是对领域不熟悉的新手。本技能同时完成：

1. 用简洁准确的人话解释测试涉及的领域术语。
2. 按“测试类别”解释测试用例究竟在验证什么。
3. 对照 `xctest-rules.md` 审核测试用例。
4. 每次只提出一个风险点，以直接文本提问让用户裁决（交互方式参照 [dd-docreview-grilling](../dd-docreview-grilling/SKILL.md) 的逐条裁决纪律）。
5. 用户裁决后执行该裁决，再继续下一风险点；当前类别审完再进入下一类。
6. 不得一次性输出全部问题，不得替用户批量做决定。

## 输入

必须读取：

- 待审核的 XCTest 测试文件
- `xctest-rules.md`
- [dd-docreview-grilling](../dd-docreview-grilling/SKILL.md) 技能

用户提供时必须读取：

- 领域需求
- 设计文档
- 测试用例表
- 规范或验收标准

为验证代码路径所必需时读取：

- 被测源码
- Fixture、Mock、Stub
- 测试辅助工具和测试资源
- 现有 TODO 文件或 `docs/AI/later/` 条目

没有领域权威文档时，可以审核 XCTest 结构和测试有效性，但不得声称某领域行为“按需求必须覆盖”。

缺少某项输入时：

- 不得猜测其内容，明确说明缺少什么。
- 在仍可继续的范围内进行审核。
- 只有确实无法判断当前风险点时，才以文本提问请求补充信息。

## 核心执行原则

### 面向新手

默认用户不了解领域术语、XCTest 细节和被测实现。解释必须：

- 先说“它是什么”，再说“为什么需要它”，再说“当前测试如何验证它”。
- 使用短句和具体例子；避免只复述测试函数名或源码。
- 不得用更多陌生术语解释一个陌生术语；必须使用专业术语时，先给一句人话定义。
- 不因面向新手而牺牲技术准确性。

### 证据优先

所有结论必须区分来源：已由测试代码直接证明 / 已由被测源码直接证明 / 已由需求或规范要求 / 来自 `xctest-rules.md` / 审核者改进建议 / 当前无法确认的推测。不得把“建议”描述成“现有规则要求”。

不得只根据测试名称判断覆盖情况，必须查看：测试输入、执行动作、断言、错误类型或错误码、测试资源、被测代码路径、是否真正触发目标分支。

### 一次只处理一个风险点

<HARD-GATE>
- 每轮只能提出一个风险点，只能提出一次裁决问题。
- 用户没有回答当前问题前，不得继续下一个风险点。
- 不得在同一个问题中捆绑多个独立裁决。
- 不得提前列出“后面还有哪些问题”，不得一次给出完整审核问题清单。
- 不得为了减少交互而合并风险点。
- 未经用户回答，不得从“提出裁决问题”跳到“继续下一风险点”。
</HARD-GATE>

唯一例外：类型 B 的两轮裁决（B1 规则治理、B2 当前测试处置）仍针对同一个风险点，每轮仍只问一个问题，期间不得切换到下一风险点。

“一个风险点”＝可以独立裁决、独立修复、独立进入 TODO 或 LATER 的最小问题。

## 测试类别划分

开始审核前，先根据测试内容识别类别，例如：正常输入、边界值、非法输入、错误传播、状态转换、数据截断、编码或解码、并发、性能、资源释放、回归、Fixture 或测试辅助代码、参数化或批量测试。

分类必须以实际测试语义为准，不得机械依赖函数名。同一测试可能涉及多个方面，但必须指定一个主要类别，避免重复审核。

## 循环状态机

必须按以下顺序循环：

1. 读取输入文件和相关技能。
2. 建立测试类别清单。
3. 选择第一类测试。
4. 解释当前类别必需术语。
5. 用人话解释当前类别测试。
6. 给出当前类别事实概览。
7. 找出当前类别最高优先级的一个风险点；若按风险检查清单没有发现有证据支持的风险点，走“无风险分支”。
8. 判断它属于：现有规则已覆盖（类型 A）；规则未覆盖但值得新增通用规则（类型 B）；规则未覆盖且不适合新增通用规则（类型 C）。
9. 输出该单一风险点的证据、解释和建议。
10. 以文本提问请求用户裁决。
11. 等待用户裁决。
12. 执行用户裁决。
13. 继续当前类别的下一个风险点。
14. 当前类别没有未处理风险后，停止当前类别；不输出类别小结；询问用户是否进入下一类测试（不得自动进入，需用户明确说才执行）。
15. 仅在所有类别均完成且用户明确要求收尾时，才输出最终总结（不自动输出）。

无风险分支：

1. 不得为了满足交互格式而虚构风险。
2. 不提出裁决问题。
3. 停止当前类别；不输出类别小结；询问用户是否进入下一类测试（不得自动进入，需用户明确说才执行）。
4. 最终总结仅在用户明确要求收尾时输出，不自动输出。

步骤 4～6 的解释与概览格式见 [references/explain-categories.md](references/explain-categories.md)。
步骤 7～10 的检查清单、优先级、类型 A/B/C 处理与裁决提问要求见 [references/risk-review-and-ask.md](references/risk-review-and-ask.md)。
步骤 12～16 的 TODO/LATER 记录与最终输出格式见 [references/todo-later-and-outputs.md](references/todo-later-and-outputs.md)。

## 风险优先级

风险点按以下顺序选择（高到低）：

1. 测试结论错误或与需求相反。
2. 测试没有触发声称验证的代码路径。
3. 测试可能稳定通过，但实际缺陷仍存在。
4. 断言错误或明显不足。
5. 测试存在不稳定性或顺序依赖。
6. Fixture 与真实输入语义不一致。
7. 缺少关键边界或错误场景。
8. 测试职责混杂。
9. 命名、结构和可维护性问题。
10. 风格类改进。

不得优先讨论格式或命名，而忽略测试正确性问题。

## 修改边界

除非用户在裁决提问中明确批准，否则不得修改：测试文件、`xctest-rules.md`、TODO、LATER、需求、设计或源码；也不得顺手修复相邻问题。

执行获批修改时：只修改当前获批事项，不夹带其他重构；修改后重新读取文件核对；说明修改位置和结果；然后继续下一风险点。

用户选择 TODO 后不得立即修改代码；用户选择 LATER 后不得继续把它当当前阻塞项。

## 禁止事项

- 一次性列出全部风险点；一次提问询问多个问题。
- 未读取规则文件就声称违反规则；把个人偏好冒充现有规则。
- 把领域行为缺口错误地写入 XCTest 通用规则。
- 仅根据函数名判断测试内容；只检查代码风格，不检查测试有效性。
- 未经批准直接改文件。
- 当前问题未裁决就跳到下一问题；为了“完整”而一次输出大批问题。
- 使用过度专业化、对新手不友好的解释。

## 首次响应格式

首次执行时，仅输出：

1. 已读取的文件。
2. 测试类别划分。
3. 第一类测试所需的少量术语。
4. 第一类测试在做什么。
5. 第一类测试的事实概览。
6. 当前类别第一个风险点；如果没有风险，则不输出小结，询问用户是否进入下一类测试。
7. 仅在存在风险点时提出一次裁决问题（文本提问）。

不要在首次响应中输出完整审核报告。
