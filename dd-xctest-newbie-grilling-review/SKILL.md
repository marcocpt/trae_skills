# XCTest 新手向交互式审核

## 目标

用户是对领域不熟悉的新手。本技能同时完成：

1. 用简洁准确的人话解释测试涉及的领域术语。
2. 按“测试类别”解释测试用例究竟在验证什么。
3. 对照 `xctest-rules.md` 审核测试用例。
4. 每次只提出一个风险点。
5. 用户裁决后执行该裁决，再继续下一风险点；当前类别审完再进入下一类。
6. 不得一次性输出全部问题，不得替用户批量做决定。

## 输入

必须读取：

- 待审核的 XCTest 测试文件
- `xctest-rules.md`

用户提供时必须读取：

- 领域需求
- 设计文档
- 测试用例表
- 规范或验收标准

为验证代码路径所必需时读取：

- 被测源码
- Fixture、Mock、Stub
- 测试辅助工具和测试资源
- 现有 TODO 文件或 `docs/AI/later/` 条目

没有领域权威文档时，可以审核 XCTest 结构和测试有效性，但不得声称某领域行为“按需求必须覆盖”。

缺少某项输入时：

- 不得猜测其内容，明确说明缺少什么。
- 在仍可继续的范围内进行审核。
- 只有确实无法判断当前风险点时，才提问请求补充信息。

## 核心执行原则

### 面向新手

默认用户不了解领域术语、XCTest 细节和被测实现。解释必须：

- 先说“它是什么”，再说“为什么需要它”，再说“当前测试如何验证它”。
- 使用短句和具体例子；避免只复述测试函数名或源码。
- 不得用更多陌生术语解释一个陌生术语；必须使用专业术语时，先给一句人话定义。
- 不因面向新手而牺牲技术准确性。

### 证据优先

所有结论必须区分来源：已由测试代码直接证明 / 已由被测源码直接证明 / 已由需求或规范要求 / 来自 `xctest-rules.md` / 审核者改进建议 / 当前无法确认的推测。不得把“建议”描述成“现有规则要求”。

不得只根据测试名称判断覆盖情况，必须查看：测试输入、执行动作、断言、错误类型或错误码、测试资源、被测代码路径、是否真正触发目标分支。

### 风险点展示格式：完整代码 + 上方注释行（MUST）

说明任何风险点时，必须给出被测测试方法的**完整源码**（整块代码，不删减），并在问题语句**上方的独立注释行**用 `// ⚠️` 标注问题点；**不得把代码打散成片段后配大段文字，也不得把注释追加在代码行尾**。

- 完整源码：整个测试方法原样贴出，保留原注释；
- 上方注释行：在具体语句上方单独一行标注问题（如 `// ⚠️ 断言与 strict 域契约相反：indirect 成功态 declaredLength 必非 nil`），让读者一眼看到「哪一行、什么问题」；注释独立成行、不跟在代码后面，避免长代码行 + 长注释在手机上换行难读；
- 代码块之后只补充少量文字要点（1~3 条），不重复上方注释已说的内容；
- 适配手机阅读：代码块紧凑、上方注释用 `//` 单行；禁止用宽表格替代代码展示；若确需逐段解释，仍须先贴完整代码，再用短列表补充。

反例（禁止）：① 把测试方法切成 5 段，每段配一段解释文字；② `let x = foo() // ⚠️ 长注释...` 这类行尾注释（手机换行后对不上代码行）。

本规则适用于：类型 A/B/C 的风险点四段输出、首次响应格式步骤 6，以及 TODO/LATER 记录中引用测试代码时；ChatGPT 送审内容不含代码（传输见「ChatGPT 外部审核」）。

### 一次只处理一个风险点

<HARD-GATE>
- 每轮只能提出一个风险点，只能提出一次裁决问题。
- 用户没有回答当前问题前，不得继续下一个风险点。
- 不得在同一个问题中捆绑多个独立裁决。
- 不得提前列出“后面还有哪些问题”，不得一次给出完整审核问题清单。
- 不得为了减少交互而合并风险点。
- 未经用户回答，不得从“提出裁决问题”跳到“继续下一风险点”。
</HARD-GATE>

唯一例外：类型 B 的两轮裁决（B1 规则治理、B2 当前测试处置）仍针对同一个风险点，每轮仍只问一个问题，期间不得切换到下一风险点。

“一个风险点”＝可以独立裁决、独立修复、独立进入 TODO 或 LATER 的最小问题。

## 测试类别划分

开始审核前，先根据测试内容识别类别，例如：正常输入、边界值、非法输入、错误传播、状态转换、数据截断、编码或解码、并发、性能、资源释放、回归、Fixture 或测试辅助代码、参数化或批量测试。

分类必须以实际测试语义为准，不得机械依赖函数名。同一测试可能涉及多个方面，但必须指定一个主要类别，避免重复审核。

## 循环状态机

必须按以下顺序循环：

1. 读取输入文件和相关技能。
2. 建立测试类别清单。
3. 选择第一类测试。
4. 解释当前类别必需术语。
5. 用人话解释当前类别测试。
6. 给出当前类别事实概览。
7. 找出当前类别最高优先级的一个风险点；若按风险检查清单没有发现有证据支持的风险点，走“无风险分支”。
8. 判断它属于：现有规则已覆盖（类型 A）；规则未覆盖但值得新增通用规则（类型 B）；规则未覆盖且不适合新增通用规则（类型 C）。
9. 输出该单一风险点的证据、解释和建议。
10. 调用 mcp chatgpt-review 发起外部审核（传输契约见「ChatGPT 外部审核」）。`content` 必须包含：风险点、被测源码与测试的文件/符号定位、规则/需求依据、AI 自己的初步判断、修改边界；代码由 ChatGPT 经 Tunnel 自行读取，不粘贴进 content。收到 reviewer 结果后不得机械接受，必须将 reviewer 证据与本地源码重新核对，再将「ChatGPT 意见 + AI 核对结论」一并展示给用户，最终裁决权仍在用户。
11. 提问请求用户裁决。
12. 等待用户裁决。
13. 执行用户裁决。（若裁决为「立即修复」且修改涉及**被测源码**，执行修复后必须按「修复后强制复审」送审，直到 reviewer 明确满意，才可标记该风险点闭环并继续下一风险点）
14. 继续当前类别的下一个风险点：若当前类别还有未处理风险点，跳回步骤 7 执行。
15. 当前类别没有未处理风险后，停止当前类别；不输出类别小结；询问用户是否进入下一类测试（不得自动进入，需用户明确说才执行）。
16. 仅在所有类别均完成且用户明确要求收尾时，才输出最终总结（不自动输出）。

无风险分支：

1. 不得为了满足交互格式而虚构风险。
2. 不提出裁决问题。
3. 停止当前类别；不输出类别小结；询问用户是否进入下一类测试（不得自动进入，需用户明确说才执行）。
4. 最终总结仅在用户明确要求收尾时输出，不自动输出。

步骤 4～6 的解释与概览格式见 [references/explain-categories.md](references/explain-categories.md)。
步骤 13～16 的 TODO/LATER 记录与最终输出格式见 [references/todo-later-and-outputs.md](references/todo-later-and-outputs.md)。

## 风险优先级

风险点按以下顺序选择（高到低）：

1. 测试结论错误或与需求相反。
2. 测试没有触发声称验证的代码路径。
3. 测试可能稳定通过，但实际缺陷仍存在。
4. 断言错误或明显不足。
5. 测试存在不稳定性或顺序依赖。
6. Fixture 与真实输入语义不一致。
7. 缺少关键边界或错误场景。
8. 测试职责混杂。
9. 命名、结构和可维护性问题。
10. 风格类改进。

不得优先讨论格式或命名，而忽略测试正确性问题。

## 风险检查清单

对当前测试类别逐项检查：

1. 测试是否真的触发目标代码路径。
2. 测试名称是否准确反映行为。
3. Arrange、Act、Assert 是否清晰。
4. 断言是否足够精确。
5. 是否存在只断言 success、非空或不崩溃的弱断言。
6. 是否遗漏错误类型、错误码、位置、长度或关联值。
7. 是否把多个独立行为塞进一个测试。
8. 是否存在测试间状态依赖。
9. 是否依赖执行顺序、时间、线程调度或不稳定环境。
10. Fixture 是否可能失真。
11. 是否只覆盖表面结果，没有验证关键副作用或状态。
12. 是否缺少必要的边界值、非法输入或回归场景。
13. 是否存在与需求、设计或被测实现不一致的假设。
14. 是否存在“测试通过，但目标缺陷仍可能存在”的假阳性。
15. 是否存在测试名称、注释和实际行为不一致。
16. 是否存在重复覆盖但关键路径仍空缺。
17. 是否违反 `xctest-rules.md`。
18. `xctest-rules.md` 是否缺少应当长期约束的通用规则。

发现风险后，只选择当前尚未处理的最高优先级风险点进行提问（优先级顺序见「风险优先级」）。若检查后没有发现有证据支持的风险点，按「无风险分支」处理，不得虚构风险。

## 类型 A：`xctest-rules.md` 已覆盖

当风险点已经被 `xctest-rules.md` 明确覆盖时，先输出四段：

### 风险点

说明具体测试、具体位置和具体问题。

### 人话解释

说明为什么这是风险，以及可能导致什么假阳性、假阴性或维护问题。

### 规则依据

指出对应规则编号或原文位置。

### 建议

给出一个明确、可执行的修改建议。

然后按「裁决提问要求」以标准四选项（`加入 TODO` / `加入 LATER` / `立即修复` / `不采纳`）提问。问题必须只针对当前这一个风险点。不得询问是否更新 `xctest-rules.md`，因为该风险已经被现有规则覆盖。

## 类型 B：`xctest-rules.md` 未覆盖，但建议新增规则

只有同时满足以下条件，才可提出更新规则：

1. 问题不是当前测试文件的偶然特例。
2. 未来其他测试也很可能重复出现。
3. 可以形成明确、可执行、可检查的通用规则。
4. 新规则不会与现有规则重复。
5. 新规则属于 XCTest 测试治理范围，而不是领域需求或实现设计。

先输出四段：

### 规则缺口

说明现有 `xctest-rules.md` 为什么没有覆盖该问题。

### 当前测试中的证据

指出哪个测试暴露了这个缺口。

### 为什么值得成为通用规则

说明它为何可能在其他测试中重复发生。

### 建议规则文本

给出可以直接写入 `xctest-rules.md` 的规则草案，包括：建议规则编号或插入章节、MUST/SHOULD/MAY 强度、规则正文、适用范围、允许的例外、正例、反例、审核检查方法。

然后以文本提问，对该风险点进行两个连续裁决。两轮仍是同一个风险点，期间不得切换到下一风险点，但两个动作不得塞进同一个问题。

**B1. 规则治理裁决**

询问“是否更新 `xctest-rules.md`，加入以上规则？”选项（推荐项按「推荐选项选择规则」确定）：

- `立即更新规则`：批准后写入规则，更新完成后必须重新读取更新后的规则文件。
- `规则更新加入 TODO`：认可规则价值，但本轮先登记。
- `规则更新加入 LATER`：规则暂缓，延后评估。
- `不更新规则`：不认可该规则，但不影响 B2 对当前测试的处置。

在用户明确选择“立即更新规则”之前，不得修改 `xctest-rules.md`。

**B2. 当前测试处置裁决**

完成 B1 后，仍围绕同一个风险点，询问当前暴露风险的测试如何处理（新增规则不会自动修复当前测试）：

- `立即修复当前测试`
- `加入 TODO`
- `加入 LATER`
- `不处理当前测试`

只有 B1、B2 都完成后，才将该风险标记为已裁决，并进入下一风险点。

## 类型 C：现有规则未覆盖，且不适合新增通用规则

适用于领域需求缺口、特定实现风险、特定测试文件问题或一次性回归场景。典型例子：某个领域边界没有对应测试、某项需求 AC 未被覆盖、某个领域 Fixture 构造错误。这些问题不具备跨项目通用性，不得写入 `xctest-rules.md`。

先输出四段：

### 风险点

说明具体测试、位置和问题。

### 人话解释

说明为什么该测试尚未证明目标行为。

### 证据依据

指出对应需求、设计、规范、被测源码或实际代码路径。若没有权威依据，明确标记为“审核建议”，不得伪装成硬性要求。

### 建议

给出可执行的新增测试或修改方案。

然后按「裁决提问要求」以标准四选项提问（推荐项按「推荐选项选择规则」确定）。

## 裁决提问要求

所有裁决每次提问必须：

- 只包含一个风险点。
- 列出 2～4 个互斥选项并编号，方便用户直接回复编号或选项文字。
- 标出推荐选项。
- 每个选项附一句影响说明。
- 不使用模糊选项，例如“看情况”“随便”“其他都行”。
- 不替用户自动选择。
- 用户回答含糊或无法对应任何选项时，重新提问，不得猜测裁决。
- 用户回答后，先执行该裁决，再进入下一风险点。

提出裁决问题前，先按「ChatGPT 外部审核」把该风险点的完整上下文发给外部 ChatGPT 辅助裁决。

提问示例：

```text
该风险点如何处理？
1. 加入 TODO（推荐）——本轮先登记，当前阶段内修复。
2. 加入 LATER——问题成立，但暂不进入当前阶段。
3. 立即修复——现在直接修改测试。
4. 不采纳——认为风险可接受。
请回复编号或选项文字。
```

若用户选择“不采纳”，记录不采纳理由；用户没有给出理由时，不强制追问，继续下一项。

## ChatGPT 外部审核

提出裁决问题前，通过 mcp chatgpt-review 把该风险点的完整上下文发给外部 ChatGPT 辅助裁决。

### 必须发送的内容

`content` 必须包含以下六项业务上下文；**不粘贴代码与 diff**，代码由 ChatGPT 按 [gpt-grilling-review](../gpt-grilling-review/SKILL.md) 传输合同经 Tunnel 自行读取：

1. 风险点：具体测试、位置和问题。
2. 被测源码定位：被测实现文件路径 + 关键符号/行范围。
3. 测试定位：测试文件路径 + 测试方法名。
4. 规则/需求依据：`xctest-rules.md` 规则编号、需求 AC 或设计条款的文件与条款位置；没有权威依据时标记为“审核建议”。
5. AI 自己的初步判断：对风险类型（A/B/C）、严重程度和推荐处置的判断。
6. 修改边界：当前任务的修改权限范围（见「修改边界」）。

### 调用方式

传输合同（`chatgpt_send` 提交 → `chatgpt_get_result` 按 `task_id` 长轮询取结果、复用同一 `conversation_id`（如 `xctest-review`）、超时与失败处置）以 [gpt-grilling-review](../gpt-grilling-review/SKILL.md) 为唯一属主，不在此重复。

### 结果处理

- 不得机械接受 reviewer 结论。
- 必须将 reviewer 给出的证据（引用的代码、规则、断言）与本地源码逐项重新核对；reviewer 引用错误或不适用于本地时，明确指出。
- 将「ChatGPT 意见 + AI 核对结论」一并展示给用户供参考，不自动采用。
- 最终裁决权仍在用户；展示后回到审核流程继续提问。
- 裁决为「立即修复」且修改涉及被测源码时，修复后的复审走「修复后强制复审」流程（送审内容、核对与迭代要求见该节）。

## 推荐选项选择规则

推荐项不得固定（不得总是推荐“加入 TODO”或“立即更新规则”），按以下规则确定：

- 当前任务允许修改，且风险导致测试结论错误或假阳性：推荐“立即修复”。
- 当前任务为只读审核，且风险应在当前阶段处理：推荐“加入 TODO”。
- 风险低优先级且不影响当前 Gate：可以推荐“加入 LATER”。
- 只有通用性、可执行性和重复发生概率都充分时，才推荐“立即更新规则”。

## 修改边界

除非用户在裁决提问中明确批准，否则不得修改：测试文件、`xctest-rules.md`、TODO、LATER、需求、设计或源码；也不得顺手修复相邻问题。

执行获批修改时：只修改当前获批事项，不夹带其他重构；修改后重新读取文件核对；说明修改位置和结果；然后继续下一风险点。

用户选择 TODO 后不得立即修改代码；用户选择 LATER 后不得继续把它当当前阻塞项。

## 修复后强制复审（修改涉及源码时 MUST）

当裁决为「立即修复」且修改涉及**被测源码**（不只测试文件，含映射表、解析逻辑、契约行为等）时，修复完成后**必须**走以下复审闭环，reviewer 明确满意前不得宣称该风险点闭环、不得提交收尾结论：

1. **提交前先送审**：将「修复涉及文件与测试的路径 + 修改范围说明 + 修复依据（规范/需求条款）+ 验证结果（lint / test 输出）」发给 ChatGPT 复审（传输按 [gpt-grilling-review](../gpt-grilling-review/SKILL.md) 的针对性复查合同，复用同一 `conversation_id`；修改后代码与实际 diff 由 ChatGPT 经 Tunnel 自行读取），要求 reviewer 明确回答「满意 / 不满意 + 具体问题清单」。
2. **逐项核对**：reviewer 引用的每个规范条款、映射值、行号、测试名，一律当场用 Read / Grep / WebSearch 验证，属实则采纳、有误则指出并说明理由，不得机械接受（同「ChatGPT 外部审核」结果处理）。
3. **迭代直到满意**：reviewer 提出修改意见 → 逐项处置（采纳修复，或不采纳并给出契约/需求依据说明理由）→ 修改后重新送审 → 重复，直到 reviewer 明确回复「满意」。reviewer 的「有条件满意」不算满意：未裁决项必须显式处理（采纳、说明立场、或登记待用户裁决），处理后再送审确认。
4. **同步检查相关需求等文档**：修复改变领域行为/契约时（新增容错策略、冻结规范勘误、变更映射/默认值、改变错误语义等），**必须同步检查**相关需求（如 `P{n}_01`）、设计（`P{n}_02`）、测试用例表（`P{n}_03`）是否需要更新或在 TODO/LATER 登记（如 `CHARACTERIZATION` / `CONTRACT_NOT_FROZEN` 标记、勘误冻结决策、undefined 字节处置契约），不得让测试冻结未经批准的行为契约。检查结果写入 TODO 文件或报告给用户。
5. **验收记录**：复审闭环后，将「reviewer 最终意见 + AI 核对结果 + 处置动作 + 文档同步结果」记录到 TODO 文件，再执行提交。

## 禁止事项

- 一次性列出全部风险点；一次提问询问多个问题。
- 未读取规则文件就声称违反规则；把个人偏好冒充现有规则。
- 把领域行为缺口错误地写入 XCTest 通用规则。
- 仅根据函数名判断测试内容；只检查代码风格，不检查测试有效性。
- 未经批准直接改文件。
- 当前问题未裁决就跳到下一问题；为了“完整”而一次输出大批问题。
- 使用过度专业化、对新手不友好的解释。
- 修改被测源码后不送 ChatGPT 复审就宣称风险点闭环（见「修复后强制复审」）。
- 修复源码改变行为/契约后，不同步检查相关需求/设计/测试用例表文档或登记 CHARACTERIZATION / CONTRACT_NOT_FROZEN / LATER。

## 首次响应格式

首次执行时，仅输出：

1. 已读取的文件。
2. 测试类别划分。
3. 第一类测试所需的少量术语。
4. 第一类测试在做什么。
5. 第一类测试的事实概览。
6. 当前类别第一个风险点（含证据、解释和建议）；如果没有风险，则不输出小结，询问用户是否进入下一类测试。
7. 按「ChatGPT 外部审核」发送并展示外部审核结果与 AI 核对结论。
8. 仅在存在风险点时提出一次裁决问题（文本提问）。

不要在首次响应中输出完整审核报告。
