# 文件任务队列

让已经运行的 agent 从共享本地目录领取一个有边界的任务，交付文件后由主模型验收。默认队列为项目 `docs/AI/tasks/`；用户指定位置优先。任务看板沿用项目原入口，不另建进度镜像。

本技能只拥有**派单和收件协议**，不替代项目规格、授权、工作流状态或 Gate。Feature/Bug 等父工作流仍使用其已有持久入口；执行包字段与来源批准沿用 [执行包合同](../dd-workflow-runtime/references/artifact-source-and-packet.md)，不因进入 pending 就视为批准。

## 先确定角色

- **主模型**：发布任务、解决范围和共享文件冲突、验收、整合和关闭。需要格式时读 [队列协议](references/queue.md)。
- **执行 agent**：扫描 pending，按下面步骤领取、完成一个任务。不要替主模型通过验收，也不要因存在待办就自动启动别的会话。

## 执行 agent 怎么接任务

1. 找用户指定队列或当前项目 `docs/AI/tasks/`。不存在或没有可领取任务，简短返回；不要自建待办、轮询死等或猜另一个仓库。
2. 阅读候选 `task.json`、`prompt.md` 与项目规则。只选目标、依赖、写入范围、输入身份与执行授权都明确的任务。核对当前工作树和来源，不能仅凭任务元数据决定可以写代码。
3. 用本技能目录下的工具领取：

   ```text
   python3 <skill-dir>/scripts/queue.py --queue <队列绝对路径> claim <任务ID> --owner <app/会话标识>
   ```

   工具验证已验收依赖，阻止领取相同任务或与运行中任务重叠的写入范围。领取失败表示未取得执行权；不要绕过工具移动目录。成功回执中的 token 供本任务提交使用，它是协作凭据，不是安全鉴权。
4. 从 `running/<任务ID>/prompt.md` 执行。默认只生成隔离候选，源仓改动须有任务明确许可；保存原有用户改动。输出可放当前任务目录，或任务指定的外部临时目录。任务目录整体会移动，使用相对位置；外部路径不作为队列状态。恢复同一任务先核对 claim owner/token 和输入，不重复领取；不能证明是自己的任务就交主模型处理。
5. 执行任务要求的验证，报告实际命令、退出码、限制和输入漂移。缺授权、批准、输入或必要能力时交付 blocked 报告，不伪造完成。大日志/图片/候选包留外部，队列内保留包含其位置和摘要的回执。
6. 最后原子写 `DONE.json`，再执行 `submit <任务ID> --token <领取token>`。工具核对必需输出、SHA256、路径与领取时的提示词指纹，才移到 submitted。提交后不再修改。文件存在、测试通过和 `completed` 都只表示待主模型验收。

允许逐个领取后续任务，前提是用户明确要求持续处理队列；否则默认完成一个就返回。跨机器副本不是共享队列，不能靠 Git 同步取得并发锁。

## 主模型怎样继续

先 `verify <任务ID>` 检查文件完整性，再阅读报告、核对来源和实现、审查脚本并自行选择必要验证；不能直接执行交付脚本或吸收其授权推断。验收结果用 `close <任务ID> --outcome accepted|rejected --evidence <验收证据位置或结论>` 记录。只有 accepted 且 completed 才能满足后续依赖。命令只能校验文件与操作互斥，不能判断操作者是否真的具有主模型身份，也不能代替内容审查。

中断的 running 任务不因时间久就自动重抢。由主模型确认原执行者已停止、保全已有结果、重新核对输入后再发布新任务；不要手删锁或覆盖唯一证据。无关任务可继续。队列本身不启动训练、Git 交付或外发动作，也不提供定时器；需要唤醒时使用用户已授权的 app 自动化。
