# 速通模式共享合同（fast track）

只在领域速通 Skill（`dd-feature-fast-track`、`dd-bug-fast-track`）进入速通或补齐阶段时读取；正式流程不读取本文件。

## 1. 定位

本文件唯一拥有「速通模式」语义：两条泳道的划分、速通阶段的可省项与不可省清单、欠账台账 schema、补齐阶段的通用规则、恢复与红线。

领域速通 Skill 只补充领域差异（复述什么、怎么冒烟、补哪些产物），不复制本文件的通用规则，也不重写 [review-gate](review-gate.md) 的审查等级语义与 [state.md](state.md) 的通用状态字段。

速通模式不修改正式流程的 Stage 图，也不降低正式流程的验收标准。它只改变两件事：

1. **顺序**——先交付可用产物，后补齐流程产物与验证；
2. **询问密度**——一次需求对齐后不再打断，直到可用产物交付。

## 2. 两条泳道

```text
Track A 速通：需求复述对齐 → 直接实现 → 冒烟自证 → 交付可用产物
Track B 补齐：补测试与确定性验证 → 补流程产物 → 补 CI 与审查 → 补文档 → 逐条关闭欠账
```

Track A 之后**没有"到此为止"分支**：速通交付后必须进入 Track B。只有用户在补齐阶段逐条确认豁免（`waived`）的欠账才可以不补。

## 3. 速通阶段规则

### 3.1 唯一询问点

速通阶段对用户的唯一询问是需求复述对齐。复述必须能让用户一句话确认或纠正，且覆盖三件事：要解决什么问题、范围边界在哪、怎样算能用。

复述未获确认（含 null、取消、空输入）时按 [ask.md](ask.md) 的「null 输入重问」规则重问，不得默认已确认。

### 3.2 对齐之后不再打断

复述确认后到可用产物交付前：

- 不再询问、不做规格批准 Gate、不派独立审查、不做阶段复核；
- 所有需要选择的分支由执行 Agent 直接选推荐项，并把「选择 + 理由」记入 `decisions`，留到补齐阶段复核；
- 仍必须停下来询问的只有四种情况：

  1. 会产生不可逆后果或外部可见后果的动作（删除数据、force push、发布到生产、对外发送）；
  2. 项目规则或授权禁止且无推荐替代的动作——按 [runtime-contract](runtime-contract.md) 记 `not-authorized`，停在该动作边界，不阻塞速通产出；
  3. 需求自相矛盾，或缺少无法从仓库事实推断的关键输入；
  4. 实现中发现已确认的需求本身不成立——回到复述对齐，不等到补齐阶段。

除这四种情况外，任何"顺手确认一下"都是违规。

### 3.3 不可省清单

1. 需求复述已获用户确认；
2. 工作环境已确定并持久化——默认新建隔离 worktree，无法创建时才用当前工作区并记 `reason`；
3. 冒烟自证——改动路径真实跑过一次，UI 变化必须有真实路径证据（见 [ui-evidence](ui-evidence.md)）；
4. 欠账台账已写入，并与状态一起持久化。

### 3.4 速通阶段禁止的宣称

- 不得宣称"验收通过""已验证""根因已证明"；
- 速通成功只等于"已有可用产物"，不等于正式流程的任何 Gate 通过。

## 4. 欠账台账

速通阶段省掉的每一项正式流程产物或验证，必须逐条登记为欠账：

```yaml
debts:
  - id: debt-01
    kind: spec | plan | test | determinism | ci | review | docs | ui-evidence | root-cause | regression
    title: <一句话>
    why_deferred: <为什么速通阶段不做>
    close_evidence: <关闭所需证据：命令、产物路径或结论>
    status: open | closed | waived
    evidence: <关闭时填入的实际证据>
    waive_reason: <仅 waived 时必填>
```

关闭规则：

- `open → closed`：必须同时写入 `evidence`，且 `evidence` 能对应 `close_evidence` 的要求；没有证据的关闭无效；
- `open → waived`：只允许在补齐阶段由用户逐条确认，`waive_reason` 必填；速通阶段不得 waive；
- 台账与状态同一份持久化，不得只存在于会话上下文或 TodoWrite。

## 5. 补齐阶段规则

1. **顺序固定**：先补测试与确定性验证，再补流程产物，再补 CI 与审查，最后补文档；
2. **补齐不是重做**：复用速通阶段的实现与证据，只补缺失项，不重复已通过的冒烟自证；
3. **基准是已确认的需求，不是实现现状**：补齐产物以复述确认的需求为准；两者冲突时改实现，并把冲突与处置记入 `decisions`；
4. **命中升级触发器即交接**：补齐阶段发现改动命中调用方正式流程的升级触发器时，交接正式流程收尾，不在速通模式内降级处理；
5. **完成判定**：所有 `open` 欠账为 `closed` 或经用户确认 `waived`，且补齐阶段的验证绑定同一个最终 SHA。

## 6. 状态字段

在 [state.md](state.md) 通用字段之外追加：

```yaml
fast_track: true
track_phase: fast-track | backfill
requirement_confirmed: true
debts: []
decisions: []
smoke_evidence: {}
```

每个 Stage Gate 通过后按 [state.md](state.md) 原子写入。

## 7. 恢复

- 有状态 → 从第一个未满足 Gate 的 Stage 继续；
- `track_phase=fast-track` 且 `debts` 缺失或为空 → `BLOCKED`，先补台账再推进；
- `track_phase=backfill` 且存在 `open` 欠账 → 继续补齐，不回退速通结论；
- 状态缺失 → 从仓库证据推导当前阶段（已有可用产物且台账存在 → backfill，否则 fast-track），不默认从头开始。

## 8. 红线

- 未复述需求就修改项目产物；
- 速通阶段除 §3.2 四种情况外再次询问或插入复核；
- 省掉的产物不登记欠账（"反正补齐阶段会做"不算登记）；
- 无 `evidence` 把欠账标 `closed`，或在速通阶段 waive；
- 用"已经能跑起来"替代正式流程的验收结论；
- 补齐阶段照抄实现现状当规格，或用实现反向改写已确认需求；
- 把速通产出解释为 commit、push、merge 或发布授权；
- 状态未持久化就跨阶段。

## 9. 合理化借口表

| 借口 | 现实 |
|------|------|
| "用户说越快越好，那就是不用补了" | 用户要的是先可用，不是免检。省掉的每一项都进台账，补齐阶段逐条关闭或让用户逐条豁免。 |
| "欠账记在会话里就行，写文件太啰嗦" | 会话结束即丢，债就变成无主债。台账必须与状态一起持久化。 |
| "实现都写完了，规格照着写最快" | 规格基准是已确认需求。照抄实现会让缺口检查永远通过，等于没有检查。 |
| "这个选择问一句更稳妥" | 速通阶段只有 §3.2 四种情况可以问。其余按推荐项执行并记 `decisions`。 |
| "反正最后会跑 CI，中间不用停" | 顺序固定是先测试后 CI。跳过确定性验证直接跑 CI 只会得到一次无法定位的失败。 |
| "补齐时发现要改架构，顺手在速通里改完" | 命中升级触发器必须交接正式流程，不在速通里降级收尾。 |
