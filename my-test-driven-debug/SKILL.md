# 测试驱动系统化调试

## 概述

将测试驱动开发（TDD）与系统化调试相结合的完整工作流：先用测试用例复现问题，再通过科学方法定位根因并修复，全程记录分析日志。

> **职责边界**：本技能仅负责"复现 → 根因 → 修复 → 重构"。lint 检查与 git 提交由调用方负责（如 `bug-fix-workflow` 步骤 4）。独立调用时，调用者自行决定是否提交。

**核心原则：** 没有复现测试就不调试，没有根因调查就不修复，没有日志记录就不算完成。

## 何时使用

- 遇到 bug 需要修复
- 测试失败需要排查
- 异常行为需要诊断
- 用户报告了问题需要解决
- 任何需要"先复现、再修复"的场景

## 完整工作流

### 第零步：获取运行日志（前置准备）

**目标：自动收集项目运行日志作为调试依据。**

1. **获取运行日志（按优先级）**

   **优先级 1：本地日志目录**
   - 计算日志目录路径：`<worktree_dir>/AI-test/logs`
     - `<worktree_dir>` 为项目上级目录的 `<project-name>-worktrees`（如项目 `Keyboard/Macim` → 日志目录 `Keyboard/Macim-worktrees/AI-test/logs`）
   - 列出该目录下日志文件，按修改时间排序取最新一个，读取完整内容
   - 若本地存在日志文件，使用本地日志，跳过 MCP

   **优先级 2：MCP 工具**
   - 本地日志目录不存在或为空时，调用 MCP 工具获取运行日志：
     - `mcp_xcode-log_get_latest_run_log` - 获取最近一次运行日志
     - `mcp_xcode-log_get_latest_build_log` - 获取最近一次编译日志
     - `mcp_xcode-log_get_latest_test_result` - 获取最近一次测试结果
   - 没有明确要求，只获取运行日志（run log）要求读取完整的日志内容

2. **日志分析**
   - 如果成功获取到日志，分析日志中的错误信息、警告和异常
   - 将关键信息提取到调试日志文件中
   - 日志中的错误信息将作为后续根因调查的重要依据

3. **无法获取日志时**
   - 如果 MCP 工具无法获取到日志（如项目未运行过、日志不存在等）
   - 使用 AskUserQuestion 工具询问用户：
     - 请提供错误信息或问题描述
     - 请描述复现步骤
     - 是否有其他日志来源

4. **记录到日志**
   ```
   ## [前置] 运行日志获取
   - 日志来源：本地目录 / MCP / 用户提供
   - 关键错误信息：xxx
   - 警告信息：xxx
   - 异常堆栈：xxx
   ```

### 第一步：编写失败测试（TDD 红灯）

**目标：用测试用例稳定复现问题。**

1. **理解问题**
   - 仔细阅读错误信息、堆栈跟踪
   - 确认复现条件：输入、环境、前置状态
   - 记录问题现象到日志文件

2. **编写最小复现测试**
   - 写一个最小化的测试来展示 bug 行为
   - 测试名称清晰描述期望行为
   - 使用真实代码，避免不必要的 mock
   - 只测一件事

   ```typescript
   // 好的示例：清晰、最小化、测真实行为
   test('rejects empty email', async () => {
     const result = await submitForm({ email: '' });
     expect(result.error).toBe('Email required');
   });
   ```

3. **验证红灯**
   - 运行测试，确认它因正确原因失败
   - 失败信息应反映功能缺失，而非拼写错误
   - 测试通过了？说明测试了已有行为，需修改测试

4. **记录到日志**
   ```
   ## [红灯] 测试用例
   - 测试名称：xxx
   - 失败原因：xxx
   - 期望行为：xxx
   - 实际行为：xxx
   ```

### 第二步：系统化调试（根因调查）

**目标：找到根本原因，而非修症状。**

**铁律：不做根因调查，不许提修复方案。**

1. **收集证据**
   - 仔细阅读错误信息，完整阅读堆栈跟踪
   - 稳定复现问题，记录复现步骤
   - 检查近期变更（git diff、最近提交）
   - 在多组件系统中，对每个组件边界添加诊断埋点

2. **跟踪数据流**
   - 错误值从哪里产生的？
   - 谁用错误值调用了这里？
   - 持续向上追踪直到找到源头

3. **模式分析**
   - 找到同一代码库中正常工作的类似代码
   - 与参考实现逐行对比
   - 列出正常代码和问题代码之间的每一个差异

4. **假设与验证**
   - 提出单一假设："我认为 X 是根本原因，因为 Y"
   - 做最小改动来验证假设
   - 每次只改一个变量
   - 生效 → 进入修复阶段；没生效 → 提出新假设

5. **记录到日志**
   ```
   ## [根因调查]
   - 错误信息：xxx
   - 复现步骤：xxx
   - 近期变更：xxx
   - 数据流追踪：xxx
   - 假设 1：xxx → 验证结果：xxx
   - 假设 2：xxx → 验证结果：xxx
   - 根本原因：xxx
   ```

### 第三步：实施修复（TDD 绿灯）

**目标：修复根本原因，让测试通过。**

1. **实施单一修复**
   - 修复已定位的根本原因
   - 每次只改一处
   - 不做"顺便改改"的优化
   - 不捆绑重构

2. **验证绿灯**
   - 运行测试，确认测试通过
   - 确认其他测试没有被破坏
   - 确认输出干净（没有错误、警告）

3. **如果修复不起作用**
   - 少于 3 次：回到根因调查阶段，用新信息重新分析
   - 3 次或以上：停下来质疑架构，与用户讨论

4. **记录到日志**
   ```
   ## [绿灯] 修复实施
   - 修复方案：xxx
   - 修改文件：xxx
   - 测试结果：PASS/FAIL
   - 其他测试影响：xxx
   ```

### 第四步：重构（TDD 重构）

**目标：在绿灯基础上清理代码。**

- 消除重复
- 改善命名
- 提取辅助函数
- 保持测试绿灯，不添加行为

> 重构完成后本技能结束。lint 检查与 git 提交由调用方负责。

## 日志文件规范

每个调试过程必须记录到日志文件中：

- **文件位置**：项目根目录下 `debug-logs/` 目录
- **文件命名**：`YYYY-MM-DD-<简短问题描述>.md`
- **日志模板**：

```markdown
# 调试日志：<问题描述>

**日期**：YYYY-MM-DD
**状态**：进行中 / 已修复 / 已关闭

## 问题描述
<清晰描述问题现象>

## [前置] 运行日志获取
- 日志来源：
- 关键错误信息：
- 警告信息：
- 异常堆栈：

## [红灯] 测试用例
- 测试名称：
- 失败原因：
- 期望行为：
- 实际行为：

## [根因调查]
- 错误信息：
- 复现步骤：
- 近期变更：
- 数据流追踪：
- 假设与验证：
- 根本原因：

## [绿灯] 修复实施
- 修复方案：
- 修改文件：
- 测试结果：

## 总结
<修复总结和经验教训>
```

## 验证清单

在标记工作完成之前：

- [ ] 尝试获取了运行日志（MCP 或用户提供）
- [ ] 编写了复现 bug 的失败测试
- [ ] 看到测试因正确原因失败
- [ ] 完成了根因调查（不是猜测式修复）
- [ ] 修复了根本原因而非症状
- [ ] 测试通过（绿灯）
- [ ] 其他测试没有被破坏
- [ ] 完成了重构（如需要）
- [ ] 分析过程已记录到日志文件

## 红线——停下来，按流程走

- 没有失败测试就尝试修复
- 没有根因调查就提出修复方案
- 一次修多个问题
- "先临时修一下，以后再排查"
- 3 次以上修复失败仍不质疑架构
- 不记录日志就宣称完成

**以上都意味着：停下来。回到对应阶段重新执行。**
