# Task Tracking 绑定尝试入口可达性 Requirements

- Feature: tracking-binding-reachability
- Workflow ID: feature-development-20261003T053419Z-ee41fa8
- Stage: Requirements（WHAT 产品合同）
- 日期: 2026-10-03

## 1. 问题陈述

外部任务绑定合同（创建并绑定一张外部任务系统 Issue 作为跨设备任务索引）已经完整规定了绑定时机、默认动作、失败矩阵、授权边界与红线，并明确"对 Feature 与 Bug 工作流，Environment Gate 前必须已完成一次绑定尝试并把结果落盘；未尝试且未记录就通过 Gate 属违规"。

但该义务对执行者不可达：两个工作流的入口主文件与共享运行时的入口文件都没有表达该义务；Stage 层唯一存在的指令把动作完全外包给 owner 合同，未表明动作本身是"创建一张 Issue"；共享状态的通用字段表示没有为该结果预留位置；不存在任何离线可运行的判定手段。

结果：绑定尝试被静默跳过，外部任务 Issue 从未被建立，且不产生任何失败信号或提示。

## 2. 目标

让"必须尝试并记录"这一既有硬约束在实际执行中被可靠触达并可被离线判定，从而在保持失败不阻塞特性的前提下，消除静默跳过。

## 3. 非目标

- 不改变 owner 合同已定义的任何语义（时机、默认动作、字段形状、枚举词表、失败矩阵、授权范围、迁移规则、红线）。
- 不引入新的授权来源或扩大既有授权范围。
- 不实现 checkpoint 写回、Issue 关闭、看板投影三类动作。
- 不处理速通模式相关契约。
- 不引入网络或远端凭据依赖。

## 4. 术语

| 术语 | 含义 |
|---|---|
| 入口主文件 | 工作流的顶层 Skill 描述文件，即执行者首次读取的编排文件 |
| Stage 层指令 | 出现在具体 Stage 的详细规则文件中的条款 |
| owner 合同 | 唯一拥有绑定与投影语义的规范文件 |
| 绑定尝试 | 为当前工作流创建或复用一张外部任务 Issue，并记录结果 |
| 尝试已记录 | 状态中存在有效绑定，或存在带失败原因的未绑定记录 |
| 尝试未记录 | 状态中既无有效绑定，也无带失败原因的未绑定记录 |
| 可发现性 | 执行者仅读入口主文件即可知悉某项义务存在的性质 |

## 5. 功能需求

### FR-1 入口可发现性

执行者仅阅读 Feature 工作流或 Bug 工作流的入口主文件，就必须能明确知悉以下义务存在：在工作流建立执行环境之后、该阶段 Gate 之前，必须为本工作流完成一次绑定尝试。

知悉义务不等于知悉全部执行细节；执行细节仍由 owner 合同唯一拥有。

### FR-2 动作明确性

入口层与 Stage 层的指令必须直接表明该动作包含"创建一张外部任务 Issue"，不得仅表述为"执行 owner 合同定义的尝试"而使动作本身不可知。

消费方不复制 owner 语义的原则保持不变；本条只要求动作可被识别。

### FR-3 运行时入口一致性

共享运行时必须在其工作流调用契约与前置检查中表达：对声明了该义务的工作流类型，建立执行环境阶段之前必须完成一次绑定尝试。

运行时当前仅在"已存在绑定"时才读取 owner 合同，该读取属恢复路径，不得作为唯一的入口表述。

### FR-4 状态可表示性

共享状态的通用字段表示必须为绑定尝试结果预留位置，使执行者首次写入状态时即产出结构上能够容纳尝试结果的状态，而不是产出结构上无处记录尝试结果的状态。

预留位置不得改变既有字段的语义或取值范围。

### FR-5 机械可判定

必须提供一个可离线运行的确定性判定手段，其输入为工作流状态，其输出为"尝试已记录"或"尝试未记录"的结论。

该手段必须能被自动执行并以非零退出状态表示不通过，以便作为阶段 Gate 的确定性证据。

### FR-6 失败不阻塞

该判定手段只在"尝试未记录"时判定为不通过。

下列情形一律判定为通过，且工作流照常推进：远端不可达、远端无法解析、Issue 缺失、项目未授权、用户拒绝创建、绑定歧义、创建结果不确定、无可用远端、凭据或服务不可用、用户明确禁用，以及历史状态不确定（本次改动之前持久化的旧状态）。

### FR-7 历史状态兼容

对本次改动生效之前持久化的状态，该判定手段不得判定为不通过，也不得据其触发任何远端创建动作。

### FR-8 单一事实源

该判定手段内部出现的任何字段名、枚举取值与原因词表，必须与 owner 合同逐项一致，且必须有自动化机制在两者出现漂移时使验证失败。

该手段不得成为语义的第二属主：owner 合同未规定的判定分支，判定手段不得自行发明。

### FR-9 覆盖对称

Feature 工作流与 Bug 工作流的入口可发现性要求完全对称。

两个工作流的入口层可发现性都必须有自动化断言保护；任一入口丢失该义务表述时，验证必须失败。

### FR-10 有效性判定链闭合

仅提供判定手段不足以生效。入口层必须明确要求在该阶段 Gate 前运行该判定手段，并把其通过结论作为 Gate 条件之一，使"未运行"与"运行但不通过"同样无法静默通过该阶段。

## 6. 验收标准

| AC | 验收条件 | 验证方式 |
|---|---|---|
| AC-01 | 仅读 Feature 工作流入口主文件即可定位到"建立执行环境阶段必须完成一次绑定尝试"的义务 | 对入口文件存在该义务表述的断言，且该表述位于执行者首读范围内 |
| AC-02 | 仅读 Bug 工作流入口主文件即可定位到同一义务 | 同上，对 Bug 入口 |
| AC-03 | 两个入口的义务表述都直接表明动作包含创建一张外部任务 Issue | 断言表述中出现该动作的明确指称，而非仅指向 owner 合同 |
| AC-04 | 两个入口都把该义务列为阶段 Gate 条件或红线 | 断言入口存在 Gate 条件或红线条目覆盖该义务 |
| AC-05 | 共享运行时入口表达"该阶段前必须完成一次尝试" | 对运行时入口存在该义务表述的断言 |
| AC-06 | 共享状态通用字段表示中存在绑定尝试结果的预留位置 | 对状态字段表示的断言 |
| AC-07 | 判定手段对"尝试未记录"的状态判定为不通过 | 判定手段的正向测试 |
| AC-08 | 判定手段对 §6 列举的每一类失败或拒绝情形判定为通过 | 判定手段对每一类情形的独立测试 |
| AC-09 | 判定手段对本次改动之前持久化的旧状态判定为通过 | 判定手段的兼容性测试 |
| AC-10 | 判定手段不进行任何网络访问或远端写动作 | 判定手段在无凭据环境下运行通过；源码不含远端调用 |
| AC-11 | 判定手段中的字段名与枚举取值与 owner 合同逐项一致 | 自动化一致性断言，owner 合同变更而判定手段未同步时失败 |
| AC-12 | 两个入口丢失义务表述时自动化验证失败 | 移除入口表述后运行验证必须失败 |
| AC-13 | 改动后仓库全部既有合同测试保持通过 | 全量既有测试运行通过 |
| AC-14 | owner 合同的既有语义未被修改 | owner 合同文件在该改动中无内容变更 |

## 7. 范围

### 7.1 范围内

- Feature 工作流入口主文件
- Bug 工作流入口主文件
- 共享运行时入口文件
- 共享状态的通用字段表示文件
- 新增的判定手段及其测试
- 两个工作流入口层与判定手段的合同测试

### 7.2 范围外

- owner 合同的任何语义修改
- 既有授权来源与授权范围的任何变化
- checkpoint 写回、Issue 关闭、看板投影的实现
- 项目级授权政策的补充
- 速通模式相关契约
- 任何 Git 交付动作（内容批准不构成 Git 授权）

## 8. 决策自由度

实现者可在以下范围内自行决定，不需再次确认：

- 判定手段的文件名、模块划分与内部函数结构
- 判定手段的输出格式与退出码的具体取值（须能区分通过与不通过）
- 入口层义务表述的具体措辞
- 合同测试的组织方式与辅助函数结构

以下不属于决策自由度，须遵守：

- 判定手段的不通过条件必须严格窄于 owner 合同的红线范围
- 判定手段不得引入 owner 合同未定义的分支或原因取值
- 不得为省减篇幅删除任何现有硬 Gate 或授权边界

## 9. 依赖与约束

- 判定手段的语义边界完全由既有 owner 合同决定，本 Feature 不重新裁决任何绑定语义。
- 项目级授权政策缺失会使 checkpoint 等后续写动作无法执行，属独立于本 Feature 的治理缺口。
- 本 Feature 不产生任何远端写动作。
