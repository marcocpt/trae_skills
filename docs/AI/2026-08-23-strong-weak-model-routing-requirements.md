# 跨 App 强弱模型协作与路由需求

> 最后更新：2026-08-23 | 版本：v1.1 | 状态：已确认需求基线

## 1. Background（背景）

用户在 Codex、ZCode、Qoder、Trae、WorkBuddy 与 OpenCode 中使用公共 Skills。不同 App 对独立 Agent 模型、推理强度、只读权限、工作区隔离、MCP 和批处理入口的支持程度不同，但用户希望保持一致的开发工作流：弱模型负责实现、确定性验证和返工，强模型负责 Review/Gate。

现有环境已经具备公共 Skill 源、Codex 弱模型 Worker 和跨 App 的外部强审能力，当前外部后端为 ChatGPT 审核。这些能力需要由统一需求约束，避免宿主配置、公共 Skill 和外部审核协议各自演化成不同工作流。

本文是该能力的需求单一事实源。下游架构由[跨 App 强弱模型协作与路由设计](2026-08-23-strong-weak-model-routing-design.md)承载，并应引用本文编号而非复制需求正文。

## 2. Problem Statement（问题定义）

1. 六个 App 没有共同的模型路由配置格式，若在公共 Skill 中写入宿主私有字段，同一工作流会产生多个不可互换版本。
2. “配置已存在”“连接可用”“审核已执行”和“finding 已关闭”容易被混为同一状态，导致未经验证的完成结论。
3. 原生 Agent、MCP 和外部调度解决的是不同问题；把它们当成互斥方案会造成宿主能力浪费或不必要的单点依赖。
4. 如果 Worker、Reviewer 和外部审核之间没有冻结基线、写入边界和有限停止条件，审查对象可能在审核期间变化，返工也可能无限循环。
5. 外部审核涉及出站任务上下文和代码访问范围，不能作为无授权的静默后台动作。
6. Skill 分发入口可能因目录收敛、改名或旧链接而失效，仅检查链接数量不能证明宿主已加载正确内容。

## 3. Goals（目标）

1. 六个 App 使用同一份公共 Skill 语义，并允许各 App 独立选择 Worker、Reviewer、模型和推理强度。
2. 建立可观察的“实现 → 确定性验证 → 强审 → 返工或完成”闭环。
3. 优先使用宿主原生能力，在能力不足或风险升级时使用公共外部强审。
4. 在不删除确定性检查和完成 Gate 的前提下，限制强模型调用次数与重复上下文消耗。
5. 让 OpenCode、MCP 和中立调度能力都可以接入同一工作流，而不成为不可替换的流程真源。
6. 保证外部审核授权、任务状态、审查证据和 finding 关闭过程可追溯、可恢复。

## 4. Scope（范围）

本次范围包含：

- Codex、ZCode、Qoder、Trae、WorkBuddy 与 OpenCode 的公共 Skill 语义一致性；
- 实现执行者、原生强审者、外部强审者和主调度者的业务角色；
- 内联自检、宿主原生强审、外部强审和自动选择四种路由方式；
- 风险自适应审查、确定性验证 Gate、finding 返工和有限停止条件；
- 外部审核前的明确授权与最小上下文边界；
- 审查基线、验证结果、覆盖范围和 finding 状态的证据要求；
- 单一 Skill 源的跨 App 分发一致性与失效检测；
- OpenCode 或其他入口发起批处理时的相同行为约束；
- 宿主能力不足、连接失败、证据不足和基线变化时的降级或阻塞行为。

## 5. Functional Requirements（功能需求）

### FR-001：公共 Skill 单一事实源

系统必须让六个 App 消费同一份公共 Skill 语义。公共 Skill 更新后，各已启用宿主必须能够获得同一份公共 Skill 修订标识；该标识必须同时区分合同语义变化和 canonical 内容变化，不要求维护可独立编辑的内容副本。

### FR-002：公共语义与模型绑定分离

公共 Skill 必须使用模型和供应商无关的角色描述。更换任一 App 的模型或推理强度时，不得要求修改公共 Skill 正文。

### FR-003：强弱角色分工

系统必须支持以下职责分离：实现执行者负责实现、运行确定性检查和按 finding 返工；强审者负责只读 Review/Gate；主调度者负责路由、状态和整体完成判断。

### FR-004：宿主独立绑定

用户必须能够为每个 App 独立选择实现执行者和强审者。一个 App 的绑定变化不得自动改变其他 App 的绑定。

### FR-005：多种审查路径

系统必须支持内联自检、宿主原生强审、外部强审和自动选择四种路径。选择不同路径时，审查语义、确定性验证要求和完成 Gate 不得改变。

### FR-006：风险自适应路由

系统必须根据任务风险、宿主能力、证据充分性和用户明确要求选择审查路径。低风险任务可以由主 Agent 完成结构化自检；跨模块、证据薄弱或结论不确定的任务必须升级独立强审；安全、权限、不可逆迁移或架构争议必须采用项目规则要求的最高审查等级。

### FR-007：确定性验证先行

进入强审前，任务要求的编译、解析、lint、测试、链接、映射或真实证据检查必须已经执行并记录。验证失败时不得消耗强审结论来替代修复，必须先返回实现执行者处理。

### FR-008：单写者与只读 Reviewer

同一任务和同一工作环境在任一时刻只能有一个实现执行者拥有写入权。强审者必须保持只读，不得在审查过程中同时修改被审查内容。

### FR-009：冻结审查基线

每次强审必须绑定明确的审查基线、变更范围和验证结果。审查期间基线发生变化时，系统必须使旧结论失效，并要求对新基线重新验证和审查。

### FR-010：结构化审查结论

每次强审必须明确返回审查通过、发现问题、等待授权或阻塞之一，并说明已审范围、未读范围、证据和下一动作。范围未完整读取时不得宣称范围审查完成。

### FR-011：finding 返工闭环

审查发现必须返回实现执行者核对和处理。修复后必须重新运行受影响的确定性验证并接受相应复审；外部强审提出且涉及生产行为或测试语义的 finding，未经外部针对性复查不得宣告关闭。

### FR-012：有限停止条件

返工和复审必须具有可配置的有限次数上限。达到上限、证据持续不足或同一阻塞条件无法解除时，系统必须停止自动循环并报告阻塞原因和下一安全动作。

### FR-013：外部强审授权

调用外部强审通道前，系统必须向用户展示将发送的任务上下文和允许访问的范围，并取得针对本次上下文的明确批准。未批准时不得发起外部审核。

### FR-014：外部审核未执行的语义

外部审核未获批准、不可用或尚未完成时，系统必须明确记录“外部审核未执行”，不得记录为外部审核通过。若外部审核不是强制 Gate，系统可以继续完成本地 Gate；若用户或项目规则明确要求外部审核，则任务必须保持未完成或阻塞。

### FR-015：宿主能力检测与降级

系统必须区分产品声称支持、当前机器已配置、连接可用、工具可发现和真实调用成功。宿主不支持独立模型时，必须选择已获准的外部路径、回到同模型模式或报告能力不足，不得静默降低审查语义。

### FR-016：Skill 分发验证

系统必须能够发现失效链接、缺失 Skill、合同版本或 canonical 内容摘要不一致，以及宿主未加载等分发问题。只有目标内容存在、修订标识一致且宿主发现验证成功，才能声明该 App 已获得公共 Skill。

### FR-017：编排入口可替换

用户必须能够从支持的原生 App 直接运行工作流，也可以选择 OpenCode、其他中立调度入口或 CI 发起批处理。关闭任一可选编排入口时，其他具备所需能力的路径必须仍可工作。

## 6. Non-functional Requirements（非功能需求）

### NFR-001：质量不降级

每次完成声明必须附带全部必需确定性验证的实际结果，并证明阻塞 finding 为零或已按项目规则取得明确处置。风险等级只能改变由谁审查和强审成本，不能删除验收条件。

### NFR-002：强模型调用节制

默认低风险任务的独立强模型调用次数必须为零；需要强审的任务必须在确定性验证通过后才发起强模型调用；同一轮外部审核在仍处于运行状态时重复提交次数必须为零。

### NFR-003：跨宿主一致性

六个目标 App 在成功安装公共 Skill 后，其分发验证结果必须报告相同的 Skill 合同版本和 canonical 内容摘要。无法支持某项原生能力的宿主必须显式报告降级路径，不得改变共同的审查和完成语义。

### NFR-004：可追溯性

每次强审记录必须包含任务标识、审查基线、变更范围、验证结果、已审与未读范围、结论和 finding 状态。缺少任一必需证据时不得宣告审查完成。

### NFR-005：可恢复性

任务中断后必须从第一个未满足 Gate 恢复，并重新核对当前仓库事实。已存在且仍有效的外部审核任务不得因连接中断而重复提交。

### NFR-006：安全与隐私

外部任务上下文的授权覆盖率必须为 100%；凭据、私钥、令牌、浏览器状态和未获准敏感内容的外发次数必须为零；不同供应商的登录凭据不得由调度流程互相转交。

### NFR-007：写入隔离

同一任务工作环境中的并发写入者数量必须始终不超过一个。需要跨 App 并行处理的任务必须使用相互隔离的工作环境或保持只读。

### NFR-008：状态准确性

配置存在、连接成功、工具发现、真实调用成功和业务 Gate 通过必须分别记录。任何较低层级的成功不得自动推导出较高层级成功。

### NFR-009：配置独立性

修改一个 App 的角色模型绑定时，公共 Skill 正文和其他 App 的模型绑定变更数量必须为零，除非用户明确要求同步变更。

### NFR-010：分发可维护性

所有已启用宿主的 Skill 分发和角色绑定都必须纳入一致性检查；检查覆盖率必须为 100%，并对每个失效或漂移项给出宿主和原因。

## 7. Constraints（约束）

### CON-001：宿主能力以当前证据为准

产品能力可能变化，实施前必须核对当前官方文档和本机配置。历史记录、配置文件存在或旧的成功结果不能单独证明当前可用。

### CON-002：现有审核语义继续有效

公共 A/B/C 审查视角以及现有 ChatGPT finding 分类、反证、复审和关闭权保持其各自事实属主；新路由能力只能引用，不得复制出第二套规则。

### CON-003：外部上下文必须最小化

外部审核只能访问本次批准范围所需的最小任务上下文。不得通过共享 OAuth token 或复制供应商登录状态实现跨 App 调用。

### CON-004：MCP 不代表工作流完成

MCP 连接或工具调用成功只证明传输层可用，不能代替工作流状态、返工循环、授权 Gate 或最终验收。

### CON-005：WorkBuddy 与 CodeBuddy 能力分别判断

WorkBuddy App 不得自动继承 CodeBuddy IDE 或 CLI 的全部能力结论；每个产品入口必须以实际暴露能力为准。

### CON-006：非 UI 能力

本需求不产生用户界面，不需要视觉原型。用户可观察证据由结构化状态、审核结果和验证记录提供。

## 8. Acceptance Criteria（验收标准）

### AC-1：公共 Skill 保持单一语义

覆盖：FR-001、FR-002、FR-016。

**Given** 六个目标 App 已按各自支持方式安装公共 Skill

**When** canonical Skill 的合同版本或内容发生变化并完成分发验证

**Then** 针对每个成功加载 App 的分发验证结果报告相同的合同版本和 canonical 内容摘要，任何失效链接、缺失内容、修订不一致或未加载宿主都被明确列出，且不存在需要独立维护的正文副本

### AC-2：单个宿主可独立更换模型绑定

覆盖：FR-002、FR-004。

**Given** 至少两个 App 已配置实现执行者和强审者

**When** 用户只更换其中一个 App 的角色模型或推理强度

**Then** 公共 Skill 正文和其他 App 的绑定保持不变，目标 App 在重新发现后使用新绑定

### AC-3：原生强弱闭环

覆盖：FR-003、FR-005、FR-006、FR-008、FR-010。

**Given** 当前 App 支持独立角色模型，且任务达到独立强审条件

**When** 用户启动任务

**Then** 实现执行者完成实现和验证，强审者只读审查冻结范围并返回结构化结论，主调度者依据结论返工或完成

### AC-4：宿主能力不足时进入外部路径

覆盖：FR-005、FR-013、FR-014、FR-015。

**Given** 当前 App 不能独立绑定强审模型，且路由策略要求强审

**When** 系统准备调用外部审核

**Then** 用户先看到具体任务上下文和访问范围；只有批准后才发起审核，未批准时按外审是否强制记录本地继续或阻塞

### AC-5：低风险任务不消耗独立强审

覆盖：FR-006。

**Given** 任务被当前策略判定为低风险，且用户和项目规则未要求独立审查

**When** 任务完成确定性验证和 A/B/C 自检

**Then** 独立强模型调用次数为零，最终结果仍包含全部必需验证证据

### AC-6：验证失败先返回 Worker

覆盖：FR-007。

**Given** 实现执行者已经完成一轮修改

**When** 任一必需确定性验证失败

**Then** 系统不进入强审完成判断，而是把真实失败证据返回实现执行者修复并重新验证

### AC-7：基线变化使旧审查失效

覆盖：FR-009。

**Given** 强审已经绑定一份冻结基线

**When** 被审查内容在结论返回前或返工后发生变化

**Then** 旧结论不能用于新基线的完成 Gate，新基线必须重新验证并接受所需审查

### AC-8：finding 完成返工与复审

覆盖：FR-010、FR-011。

**Given** 强审返回至少一个有效 finding

**When** 实现执行者完成授权范围内的修复并运行受影响验证

**Then** finding 保留原身份进入复审；涉及生产行为或测试语义的外部 finding 只有在外部针对性复查确认后才能关闭

### AC-9：返工达到上限后停止

覆盖：FR-012。

**Given** 当前任务已经达到配置的返工次数上限

**When** 仍存在未关闭的阻塞 finding 或证据缺口

**Then** 系统停止自动循环，报告阻塞原因、已有证据和下一安全动作，不重复提交相同工作

### AC-10：外部审核状态不被误报

覆盖：FR-013、FR-014。

**Given** 外部审核未获批准、不可用或仍在运行

**When** 系统生成状态或最终报告

**Then** 报告明确区分未执行、运行中和已完成，不得把任何一种记录为外部审核通过

### AC-11：能力证据逐级验证

覆盖：FR-015、FR-016。

**Given** 某个 App 存在 Skill 或 MCP 配置

**When** 执行宿主能力验证

**Then** 结果分别报告配置、连接、工具发现、真实调用和业务结论，任一缺失层级都不能由前一层成功推导

### AC-12：OpenCode 不是单点依赖

覆盖：FR-017。

**Given** OpenCode 不可用，但另一个 App 具备所需原生或外部审核能力

**When** 用户从该 App 启动相同工作流

**Then** 工作流仍按共同语义完成；当 OpenCode 可用并发起批处理时，也必须产生相同 Gate 和证据语义

### AC-13：高风险任务不能静默降级

覆盖：FR-006、NFR-001。

**Given** 任务涉及安全、权限、不可逆迁移或架构争议

**When** 当前宿主无法执行项目规则要求的最高审查等级

**Then** 系统选择获准的独立审查路径或报告阻塞，不得改用低风险自检后宣告完成

### AC-14：跨 App 写入保持隔离

覆盖：FR-008、NFR-007。

**Given** 两个 App 同时针对同一任务工作环境请求写入

**When** 第二个写入者准备修改内容

**Then** 系统只允许一个实现执行者继续写入，另一个入口必须保持只读、转入隔离环境或明确停止

### AC-15：中断后不重复提交外部审核

覆盖：FR-012、FR-014、NFR-005、NFR-008。

**Given** 外部审核已经提交且仍在运行，当前连接随后中断

**When** 工作流恢复

**Then** 系统继续查询原审核任务并恢复到第一个未满足 Gate，重复提交次数为零，状态仍记录为运行中而非通过

### AC-16：外部上下文排除敏感信息

覆盖：FR-013、NFR-006。

**Given** 待审范围同时包含获准业务文件和凭据、令牌、浏览器状态或其他未获准内容

**When** 用户批准业务文件的外部审核

**Then** 外部审核只能访问获准范围，敏感内容外发次数为零，不同供应商的登录凭据不会被调度流程转交

## 9. Out of Scope（明确不做）

- 冻结具体供应商、模型名称、推理强度或套餐价格；
- 规定各 App 的配置文件格式、目录、安装命令或界面操作；
- 由 Requirements 规定 Skills、Agent 配置、MCP 服务、中立 Router、CLI/SDK 或 CI 的具体实现形式；
- 建立无需用户批准的外部强审自动送审；
- 共享、复制或代理不同供应商的 OAuth token、浏览器登录态或其他凭据；
- 让 Reviewer 与 Worker 同时修改同一工作环境；
- 把 WorkBuddy App 与 CodeBuddy IDE/CLI 视为完全相同的能力入口；
- 在本文中生成 Implementation Plan、Test Matrix 或 UI Visual Prototype。

## 10. Terminology（术语）

| 术语 | 定义 |
|---|---|
| 公共 Skill | 被多个 App 消费、表达共同工作流语义的单一权威内容。 |
| 宿主 App | 承载用户会话、加载 Skill 并提供模型或工具能力的应用。 |
| 实现执行者 | 负责实现、确定性验证和按 finding 返工的角色。 |
| 强审者 | 负责只读 Review/Gate、给出 finding 或通过结论的角色。 |
| 原生强审 | 在当前宿主内部由独立 Agent 完成的强审。 |
| 外部强审 | 经用户授权后，由当前宿主之外的独立审核后端完成的强审；当前后端实例为 ChatGPT 审核能力。 |
| 主调度者 | 负责选择路径、推进状态、限制循环和判断整体完成的角色。 |
| 路由策略 | 根据风险、能力、证据和用户要求选择审查路径的规则集合。 |
| 确定性验证 | 编译、解析、lint、测试、链接、映射或真实证据检查等可重复验证。 |
| 冻结基线 | 某轮审查明确绑定且在结论有效期内不得变化的审查对象。 |
| finding | Reviewer 发现并要求核对、处置或复查的具体问题。 |
| Gate | 在进入下一状态或宣告完成前必须满足的条件集合。 |
| 降级路径 | 宿主缺少某项原生能力时，明确选择的替代执行方式。 |
| 配置存在 | 本地保存了相关设置，但尚不证明连接、工具发现或真实调用成功。 |
| Skill 合同版本 | 标识公共 Skill 语义兼容关系的版本；相同版本不得对应彼此冲突的公共工作流语义。 |
| canonical 内容摘要 | 对一次公共 Skill 发布所包含 canonical 内容计算出的稳定标识，用于发现内容缺失、漂移或宿主缓存不一致。 |

## 11. Decision Freedom（实现自由度）

### 允许自由决定

- 每个 App 使用的具体模型、推理强度和角色名称；
- 宿主适配配置的格式、生成方式、安装方式和刷新机制；
- 公共 Skill 修订标识的保存载体和 canonical 内容摘要的计算方式；
- 状态与证据的持久化格式；
- 原生 Agent、MCP、CLI/SDK 或 CI 的具体接入方式；
- 正整数范围内的默认返工次数上限；
- 不改变本需求语义的错误码、展示文案和内部组织方式。

### 禁止自由改变

- 禁止把供应商或具体模型绑定写入公共 Skill 语义；
- 禁止为节省 Token 删除确定性验证、A/B/C 审查语义或完成 Gate；
- 禁止让多个角色同时写入同一任务工作环境；
- 禁止在外部审核前跳过本次上下文的明确授权；
- 禁止由本地 Worker 自行关闭涉及生产行为或测试语义的外部 finding；
- 禁止把 OpenCode、MCP 或任何单一 App 变成所有工作流的强制入口；
- 禁止共享供应商凭据或把配置存在报告为真实集成通过；
- 禁止用历史状态替代当前仓库、连接和验证事实。

## 12. Future Considerations（未来扩展）

以下方向可以在不改变本文核心语义的前提下另行立项：

- 建设宿主中立的 Router，并同时提供 CLI/SDK 与 MCP 入口；
- 把强审 Gate 扩展到 PR、CI 或 nightly 批处理；
- 基于真实任务记录统计不同模型组合的成本、延迟、返工率和 finding 命中率；
- 自动检测宿主能力并生成或校验适配配置；
- 支持新增 App，而无需修改现有公共 Skill 正文；
- 建立单独 Test Matrix，覆盖六个宿主的原生、降级、授权、恢复和失效场景。
