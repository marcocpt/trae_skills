# ChatGPT 文件 Grilling 审核

## 目标

角色反转的审核闭环：**ChatGPT 是主审**（经只读通道自行读取指定文件，找问题、给意见），**本地 agent 是执行者与核对者**（逐条核对意见、分流、执行获批修改、送回复审），**用户是最终裁决人**。依据 `/Users/dengdeng/.trae-cn/skills/gpt-code-review.md` 的人工判断升级规则，对核对属实的风险点做三类分流，**仅 HUMAN_DECISION_REQUIRED 逐条裁决**，能客观判定的不升级为人工决策，以减少不必要的人工询问。

## 角色分工

| 角色 | 职责 | 禁止 |
|---|---|---|
| ChatGPT（主审） | 用其可用工具读取指定文件，输出结构化风险点与修改建议 | — |
| 本地 agent（执行+核对+分流） | 送审、逐条核对 ChatGPT 引用、按 gpt-code-review.md 分流、执行获批修改、送复审 | 不得机械接受意见；不得把可客观判定的问题升级为人工决策；不得未经授权修改 |
| 用户（裁决人） | 对 HUMAN_DECISION_REQUIRED 逐条裁决；对 FINDING 批量授权；对 VERIFICATION_REQUIRED 确认取证方式 | — |

**违反规则的字面意思就是违反规则的精神。**

## 输入

开始前必须确认（缺失则向用户提问，不得猜测）：

1. **仓库名**：按技能 gpt-review-loop 的命名规则（`cpdf` / `cpdf-wt/<分组>/<分支名>` / `work/<相对路径>`）；送审前 `git worktree list` 确认存在
2. **文件清单**：用户指定的待审文件（仓库内相对路径）；用户只给了目录或分支时，先送审"列范围"请求，拿到 ChatGPT 发现的文件清单后与用户确认
3. **可选权威依据**：需求/设计/规范文档路径（有则一并在送审内容中指明，让 ChatGPT 对照）

## 循环状态机

1. 确认输入（仓库名 + 文件清单）
2. 首次送审（见「首次送审模板」），拿到 ChatGPT 的风险点清单
3. **本地核对**：对 ChatGPT 引用的每个文件、行号、结论，用 Read/Grep 当场验证；引用有误的明确标注（不得机械接受）
4. **风险分流**：依据「风险分流规则」，把核对属实的风险点归入 FINDING / VERIFICATION_REQUIRED / HUMAN_DECISION_REQUIRED 三类
5. 按分流路径处置：
   - FINDING → 走「批量 finding 处置」
   - VERIFICATION_REQUIRED → 登记「待验证清单」，标注所需证据，不阻塞
   - HUMAN_DECISION_REQUIRED → 走「逐条裁决」（HARD-GATE 仅适用此类）
6. 任何「立即修复」执行后，走「修复后强制复审」直到 ChatGPT 满意
7. 还有未处置风险点 → 回步骤 5 对应路径；没有 → 询问用户是否扩大范围/收尾（不得自动继续）

<HARD-GATE>
- 仅对 HUMAN_DECISION_REQUIRED 类风险点逐条裁决：每轮只处理一个、只提一个裁决问题；用户未回答不得继续下一个
- 不得提前列出"后面还有哪些 HUMAN_DECISION_REQUIRED 问题"，不得一次给出全部决策项让用户批量决定
- FINDING / VERIFICATION_REQUIRED 不受逐条裁决约束，按各自路径批量登记或一次性确认
</HARD-GATE>

## 风险分流规则

分流权威依据：`/Users/dengdeng/.trae-cn/skills/gpt-code-review.md`（代码审核：人工判断升级规则）。**不得把可客观判定的问题升级为人工决策。**

### FINDING（可以客观判定，应修复）
能根据代码、测试或明确规格证明的问题：明确逻辑错误、崩溃、越界、竞态、资源泄漏、与明确规格直接冲突、明确缺少错误处理、明确违反架构规则、测试能稳定证明的问题。

- 处置：归入 finding 清单，走「批量 finding 处置」；不逐条裁决
- 正确行为明确但缺测试 → 仍归 FINDING，直接指出应补什么测试，不因测试缺失升级为人工决策

### VERIFICATION_REQUIRED（行为明确，缺运行证据）
行为定义明确，但还需 CI、真机、基准、真实语料、GUI 等证据才能确认。

- 处置：登记「待验证清单」，写明需要什么证据、建议如何获取；不阻塞当前审核
- 不得因缺证据就升级为 HUMAN_DECISION_REQUIRED

### HUMAN_DECISION_REQUIRED（正确行为需人决策）
真正涉及产品/架构/风险决策或取舍：多种合理行为无法由代码/规格确定、规格间冲突、改变用户可见行为/兼容性/公共 API、架构边界权衡、性能/精度/内存等指标取舍、依赖真实环境无法自动验证、安全/隐私/fail-open/fail-closed、不可逆操作、异常策略选择、删除旧实现/deprecated API 无授权、缺证据区分"设计如此"vs"实现错误"。

- 处置：走「逐条裁决」（HARD-GATE 适用），必须给出技术分析 + A/B（必要时 C）可选方案及优缺点 + 一个具体可回答的问题，不得只写"请人工确认"

### 分流纪律
- 不要因为"可能有问题"就升级为人工决策；能证明的直接归 FINDING
- 不要把个人编码偏好升级为人工决策
- 不要因测试缺失就自动要求人工判断；正确行为明确的，直接指出该补什么测试（归 FINDING）
- 只缺运行证据 → VERIFICATION_REQUIRED；只有真正涉及决策或取舍 → HUMAN_DECISION_REQUIRED
- 优先减少误报：只有影响正确性、交付风险、兼容性或长期架构的事项才进入分流

## 首次送审模板

调用契约（conversation_id、timeout 600、轮询、断线重连）遵循技能 gpt-review-loop。content：

```
请使用你可用的工具，自行读取仓库 "<repo>" 中的以下文件（不要依赖我提供内容）：
<文件清单，每行一个相对路径>

逐文件审核：正确性、边界处理、错误传播、与同目录其他代码的一致性；
如有提供需求/设计文档（<文档路径>），同时审核实现与文档的一致性。

输出结构化风险点列表，每条含：优先级（高/中/低）、问题描述、位置（文件:行号）、修改建议。
如果无法读取任何指定文件，直接回复一行：无法读取指定文件。
```

## 修复后复审模板（同 conversation_id 续发）

```
我已按你的第 <N> 条意见修改，请重新读取以下文件复审：
<被修改的文件清单>
修改说明：<每个文件改了什么、依据哪条意见>
请明确回答：满意，或不满意 + 具体问题清单。
```

复审规则：

- 「有条件满意」不算满意：未决项必须显式处理（采纳修复 / 说明立场 / 登记分流）后再送审
- 迭代直到 ChatGPT 明确回复「满意」，才可标记该风险点闭环
- ChatGPT 复审新发现的问题：回到状态机步骤 3，作为新风险点重新分流（不得擅自直接修）

## 风险点展示格式（MUST）

展示任何风险点时，必须给出相关方法的**完整源码**，问题语句用 `// ⚠️` 标注在**上方独立注释行**；代码块后只补 1-3 条要点。禁止：把代码打散配大段文字、行尾长注释、用宽表格替代代码。

展示内容固定四段：**ChatGPT 意见**（含其给出的优先级与建议）→ **本地核对结论**（引用属实/有误，逐条）→ **分流归类**（FINDING / VERIFICATION_REQUIRED / HUMAN_DECISION_REQUIRED + 一句理由）→ **建议处置**。

- FINDING 批量展示时，多条可紧凑列出，每条仍含位置+问题+建议修复
- HUMAN_DECISION_REQUIRED 单条展示时，在「建议处置」后接「逐条裁决提问」

## 批量 finding 处置（FINDING 类）

- 把所有 FINDING 类风险点合并展示（遵循「风险点展示格式」）
- 一次性向用户确认处置（不逐条提问）：
  - 全部立即修复
  - 全部加入 TODO
  - 按子集拆分（用户指定哪几条立即修复、哪几条加入 TODO）
- 用户授权后执行修复；未经授权不得改任何文件
- 修复完成后按「修复后强制复审」送审

## 逐条裁决提问要求（仅 HUMAN_DECISION_REQUIRED）

- 只含当前一个 HUMAN_DECISION_REQUIRED 风险点；2-4 个互斥选项编号；标推荐项；每项一句影响说明
- 提问前必须先给技术分析 + 可选方案（A/B，必要时 C）及优缺点，对齐 gpt-code-review.md 的 HUMAN_DECISION_REQUIRED 格式
- 推荐项不固定：修复导致错误结论且任务允许改 → 推荐立即修复；只读审核任务 → 推荐 TODO；低优先级 → 推荐 LATER
- 用户回答含糊 → 重新提问，不得猜测裁决
- 选项：`加入 TODO` / `加入 LATER` / `立即修复` / `不采纳`（不采纳时记录理由，不强制追问）

## 修改边界

- 未经用户授权，不得修改任何文件；不得顺手修复相邻问题
- FINDING 类经一次性授权后，只改授权范围内事项，不夹带重构；改后重新读取文件核对
- HUMAN_DECISION_REQUIRED 类经逐条裁决后，只改当前获批事项
- TODO 项不得立即改；LATER 项不得继续当阻塞项
- VERIFICATION_REQUIRED 项在取得证据前不得擅自修复

## 基线失败（无本技能时的真实错误）

| 真实失败 | 技能对策 |
|---|---|
| 机械接受 ChatGPT 意见（行号/引用错误也被照单执行） | 步骤 3 强制本地核对，引用有误必须标注 |
| 把可客观判定的 FINDING 升级为逐条人工裁决，淹没真正需要决策的问题 | 风险分流：FINDING 批量处置，仅 HUMAN_DECISION_REQUIRED 逐条裁决 |
| 一次倒出全部 HUMAN_DECISION_REQUIRED 问题，用户无法决策、修改互相打架 | HARD-GATE 仅对此类一次一个 |
| 改完不复审就宣称闭环 | 修复后强制复审，满意前不得闭环 |
| 送审不指定文件清单，审核漂移或干等粘贴 | 输入必须含文件清单 + 首次送审模板 |
| 修改时夹带无关重构 | 修改边界：只改获批事项 |
| 因测试缺失或只缺运行证据就要求人工决策 | 缺测试归 FINDING 指出补测试；缺证据归 VERIFICATION_REQUIRED |

## 红线 - 出现即停下纠正

| 借口 | 现实 |
|---|---|
| "ChatGPT 说的肯定对，直接照改" | 引用可能错；先本地核对，再分流 |
| "每个问题都得问用户才稳妥" | 能客观判定的归 FINDING 批量处置，只有真正决策项才逐条裁决 |
| "问题都差不多，一起问了效率高" | HUMAN_DECISION_REQUIRED 一次一个是硬门禁；FINDING 才可批量 |
| "修改 obvious 不用等授权" | 未经授权不得改任何文件 |
| "复审太慢，改得对就行" | 满意前不得闭环，这是流程契约 |
| "顺手把旁边的问题也修了" | 夹带 = 边界失控，新问题走新分流 |
| "缺测试/缺证据，让用户定夺吧" | 正确行为明确归 FINDING 指出补测试；只缺证据归 VERIFICATION_REQUIRED |

## 禁止事项

- 把可客观判定的问题（FINDING）升级为 HUMAN_DECISION_REQUIRED 逐条裁决
- 因测试缺失或只缺运行证据就要求人工决策（应归 FINDING 指出补测试，或 VERIFICATION_REQUIRED）
- 一次列出全部 HUMAN_DECISION_REQUIRED 风险点；一个提问捆绑多个决策
- HUMAN_DECISION_REQUIRED 不给技术分析和可选方案，只写"请人工确认"
- 未核对 ChatGPT 引用就展示或执行其意见
- 未指定文件清单就送审；把代码粘贴进 content（ChatGPT 自行读取）
- 修改后不送复审就宣称风险点闭环；「有条件满意」当作满意
- 复审发现的新问题不经过分流直接修
- 复审 content 提及通道/工具实现机制（保持业务视角）
