# 同一会话中的强弱模型协作

本模式由当前弱模型会话主持，通过 Codex/OpenCode CLI 按需调用指定强模型。强模型作技术裁决、批量验收和明确的小修复，较大实现交回当前弱模型。不新建顶层 Skill、不建立文件队列、不要求用户复制提示词，也不默认启动其他会话。

本文件拥有协作编排；CLI 输入输出、模型选择、指纹与会话校验由 [运行时调用合同](../../dd-workflow-runtime/references/strong-collaboration.md) 拥有。本模式不经过旧 `dispatch-review.py`，不得把旧 adapter 的只读豁免回执转换为本模式的关闭证据。

## 入口与调用时机

1. 从当前请求、项目规则、既有任务与源码恢复目标、范围、依据、授权、模型和已有问题；不重复询问已知事实。后端与模型显式指定；缺少模型选择时先读 共享默认配置形成具体建议，不擅自持久改绑。
2. 弱模型先做可重复的探索、实现和必要验证。能沿已批准方案推进就继续，不因每个小任务完成而调用强模型。
3. 相关任务形成**可独立验收的批次**时调用一次强审；根据耦合与验证边界划批，不按文件数、字数或固定 token 阈值划批。高风险、关键不确定性或证据薄弱按 [review-gate](../../dd-workflow-runtime/references/review-gate.md) 提前升级，不能等批量来掩盖阻塞。
4. 弱模型无法给出可靠的有边界方案时，可调用 `plan` 请求强模型拆任务；不要求未实现功能先有通过的测试。任务返回后由当前弱模型执行，不套用 advisory 的人工逐项选方案流程来阻塞已授权的技术裁决。
5. 首次实际外发前按项目要求展示具体上下文、源码访问范围和操作范围并取得批准；已有批准只覆盖相同上下文与范围，不因启用本模式而自动扩张。只读 snapshot、组包和本地验证不外发。

## 每批怎样执行

1. 保存 HEAD、status、已有差异与既有失败，明确弱模型与用户原有修改。按 runtime 合同冻结当前内容；可以包含未提交文件，不为满足审查条件自动 commit。
2. 只传必要目标、验收条件、依据锚点、真实差异定位、finding ID 与证据入口。强模型自行读取实际材料；不能只审弱模型摘要。续接仅传新增变化，但保留授权和通过条件。
3. 父会话暂停写入，调用一次 `plan`、`review` 或已授权 `repair`。若本批已预授权明确的小修复，review 可以带限定 write_scope 与 repair 策略，让强模型在同一次调用中处理小问题、大问题返回任务；仅批准只读 review 时绝不写入。大日志留原证据位置，不复制全部会话历史；按需加载 reference，不把所有工作流材料塞进提示词。
4. 核对 runtime 回执：实际原生会话身份、请求模型、范围覆盖、轮前轮后指纹、实际差异、验证结果。供应商没有报告 token 用量就记未提供，不估算成实测。
5. 按下表处置，结果与问题状态保存到父任务现有入口。不创建第二套问题台账；已有 F/V/H、DISPUTED、原问题 ID、四项 CLOSED 判据照常适用。

| 返回内容 | 当前弱模型下一步 |
|---|---|
| 完整 PASS | 核实实际源码、授权、证据和四项关闭判据，再登记相关 finding CLOSED；PASS 本身不是 CLOSED |
| 大修复 finding 与任务 | 本地核对引用和授权，执行精确任务、运行验证；相关问题完成后续接同一强审会话一次针对性复查 |
| 明确小修复候选 | 比较直接修改与交接的剩余成本；若满足下节条件且授权覆盖，调用 repair；不把“模型很强”当风险证据 |
| 同轮已修复小问题，同时还有大问题 | 核对 fixed_findings 与实际差异及验证；仅相应 ID 成为关闭候选，大问题保持 OPEN 并交回当前弱模型，不把整批当 PASS |
| F/V/H 争议 | 将反证合并进下一次针对性复查，强模型可做范围内技术裁决；未核实前不得静默改分类或关闭 |
| 正确行为未定义、范围/授权不明 | 保留现有逐条人工裁决规则；技术裁决不能创造产品语义、推翻权威规格或扩大授权 |
| BLOCKED、身份/基线漂移、超出返工上限 | 保留改动与证据，停止本轮自动循环，报告具体原因和下一安全动作，不伪装通过或自动换后端 |

## 小修复自验例外

本节是对“强审者只审”和“实现者不能验收自身修改”的**限定例外**，只用于本模式下有明确写授权的 Codex/OpenCode 强模型；弱模型不因此获得自闭环权，ChatGPT 不因此获得写权限。

必须同时满足：

- 已本地核实问题，正确行为由现有权威依据确定；任务边界和允许写入文件明确。
- `CHANGE_RISK=LOW`，不突破主 SKILL 的任何风险下限；代码行少、修复快或原问题严重度低都不能替代风险判断。
- 修复局部、方案明确；直接修复预计比解释、交接再复查更省成本。需要广泛探索、跨模块修改、修改测试期望或不确定行为时交回弱模型。
- 强模型重新核对实际源码与差异、未覆盖用户已有修改，runtime 实际运行必要验证并绑定修改后指纹。
- 明确记录这是 `strong-self-fix`，满足 CLOSED 四项判据；不宣传为独立审查。

低风险判断不能可靠成立时不启用例外。复杂或高风险的强模型亲自修改须由另一强审身份独立验收；建立新审查轮次，记录原 finding 与接管关系，重新读取真实材料，不继承旧会话关闭权。本通道的 repair 不接受这类实现。

## 控制成本而不降低质量

- 普通低风险任务不额外唤醒强模型；已经进入强审批次时，可以顺带处理符合条件的低风险小修复。
- 强模型返回任务必须含目标、写范围、步骤、验证与停止条件。当前弱模型不扩张范围、不重新发明已明确的技术方案，也不让强模型再调用强模型。
- review 前先通过必要确定性验证；repair 后重新执行受影响验证。真正的运行证据缺口仍归 V，不以补代码掩盖。
- 默认两次续接用于返工或针对性复查，失败也计入已开始的轮次；达到上限后说明剩余问题，不通过换 workflow_id 或删会话绑定绕过。
- 对每批记录实际调用次数；只有供应商提供的 usage 才记作 token 实测。节省调用的目标不等于保证 token 一定下降。

Git 交付、产品行为裁决、真实用户数据和不可逆外部动作仍遵守原授权边界。本模式的内容验收不授权 commit、push、merge、PR 或发布。
