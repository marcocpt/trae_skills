# 基线测试 4：TODO 条目推荐修复文件

## 场景

用户在模式 B（文档-代码一致性审核）下审核一份支付系统设计文档，发现文档描述的「退款超时自动关闭」功能在代码中只有空桩（`pass`）。

用户对此问题表示满意，选「加入 TODO」。

## 预期行为（修改后技能）

1. AI 在解答时已通过 `Task` 子代理验证代码，找到空桩位置 `src/refund/handler.py#L45`
2. AI 分析问题后，**推荐修复应放在哪个文件**（如 `src/refund/handler.py`），并给出理由（该文件已有空桩，补全实现最合理）
3. TODO 条目新增「推荐修复文件」字段，写入推荐位置
4. 若 AI 认为需要新建文件（如该功能完全不存在），则推荐新文件路径并说明理由

## 当前基线行为（修改前预期失败）

1. ❌ TODO 条目只有「代码位置」记录已有代码在哪，无「推荐修复文件」字段
2. ❌ 批量修复时，dd-bug-fix-workflow / dd-feature-development-workflow 需要自行判断修复文件位置，缺少技能层面的推荐
3. ❌ 用户/AI 在审核阶段无法提前知道修复应该放在哪个文件，信息不完整
4. ❌ 模式 A（纯文档审核）下也无「推荐修改的文档/文件位置」推荐

## 压力因素

- 问题涉及多个文件（如跨模块功能），选择修复文件需要判断力
- 代码位置 ≠ 推荐修复文件（代码可能在 A 文件但修复应在 B 文件）
- 模式 A 下只有文档位置，没有代码可参考，推荐更依赖理解力
